# AI 蓝军本地复现问题案例集

> 阶段：第三阶段问题复盘。  
> 真实性声明：以下15项均来自当前仓库截图整理 SQL、`pt='2026-07-11'` 本地造数或链路静态验证。它们只能表述为“本地复现和链路验证中发现的问题”，不能说成公司生产事故。  
> 生产边界：用户确认核心10张表真实上线并稳定调度，但当前材料不等于生产最终版；本文不推断生产环境是否出现过同类故障。

## 1. 复盘方法

每个案例均按以下顺序记录：

```text
现象 → 证据与复现 → 根因 → 排查 → 修复 → 验证 → 预防
```

排查原则：先判断是DDL、字段契约、数据内容、JOIN基数、写入方式还是引擎能力问题，再做最小修改；不把多个猜测一起改掉。

## 案例1：`event_code`重复定义为普通列和分区列

### 现象

审核DWD建表语句可能直接失败，或不同引擎对字段解析产生冲突；即使勉强建成，`SELECT *`和动态分区装载也容易出现列数/列序问题。

### 证据与复现

当前整理版 `dwd_com_audit_detail_df` 同时出现：

```sql
event_code STRING COMMENT '业务场景码code'
...
PARTITIONED BY (pt STRING, event_code STRING)
```

静态检查DDL字段清单即可稳定发现，不需要假设具体生产报错文本。

### 根因

Hive风格分区列属于表Schema的一部分，不应在普通字段列表中重复声明。加工SQL又同时在SELECT中间和末尾输出`event_code`，说明设计混淆了“业务字段展示”与“动态分区列写入”。

### 排查

1. `SHOW CREATE TABLE`确认实际元数据中`event_code`出现位置。
2. 对照目标表普通列数、分区列数和INSERT SELECT列数。
3. 单独执行DDL验证，不先运行INSERT。
4. 检查下游是否依赖`event_code`；分区列仍可正常查询，不需要复制成普通列。

### 修复

保留`event_code`为分区列，从普通字段列表删除；动态分区写入时只在SELECT末尾输出一次：

```sql
INSERT OVERWRITE TABLE yshopping.dwd_com_audit_detail_df
PARTITION (pt='${bizdate}', event_code)
SELECT
  audit_id,
  biz_id,
  ...,
  event_code
FROM ...;
```

### 验证

- DDL可以执行。
- `DESCRIBE FORMATTED`中`event_code`只在分区列出现一次。
- 各`event_code`分区行数之和等于过滤后的源行数。
- 抽样字段未发生整体错位。

### 预防

- 上线前自动比较普通列和分区列交集，交集必须为空。
- 禁止使用`SELECT *`写动态分区表。
- 代码评审明确“动态分区列必须位于SELECT末尾”。

### 面试表述

> 我在本地还原审核DWD时发现`event_code`既写在普通列又写在分区列。先通过DDL和列序对比定位到Schema重复，再保留为分区列并校验各分区行数。这个案例是本地复现，不是生产事故。

## 案例2：ODS使用`update_time`，DWD读取`modify_time`

### 现象

DWD任务可能报字段不存在；如果平台做了宽松映射或源版本不同，也可能表现为更新时间整列为空，进而影响取最新、增量同步和去重。

### 证据与复现

该问题来自本地不同版本的字段契约差异。当前已整理SQL多处使用`modify_time`，但问题清单记录原始/实际ODS版本曾使用`update_time`。复现方式是对比源表真实元数据与DWD引用字段，而不是只看转写文件。

### 根因

上游Schema变更或截图/文档版本不一致，没有通过数据契约同步到DWD。`update_time`和`modify_time`语义相近，使问题在人工阅读时容易被忽略。

### 排查

1. 以`DESCRIBE ods_table`或元数据平台为准，确认真实字段。
2. 搜索DWD SQL对两个字段名的引用。
3. 抽样比较创建时间、更新时间的非空率和最大值。
4. 检查增量抽取条件、`ROW_NUMBER ORDER BY`是否依赖错误字段。

```sql
SELECT
  COUNT(*) AS cnt,
  COUNT(update_time) AS update_cnt,
  MAX(update_time) AS max_update_time
FROM ods_table
WHERE pt='${bizdate}';
```

### 修复

- 若真实源字段是`update_time`，在DWD统一别名为`modify_time`：`update_time AS modify_time`。
- 若上下游正在迁移，显式做版本兼容，但只在确认两字段不会同时冲突后使用。
- 同步更新表说明、字段血缘和质量规则。

### 验证

- DWD任务不再引用不存在字段。
- ODS与DWD更新时间非空数一致。
- 最大/最小时间范围合理，无未来时间和全量1970时间。
- 取最新逻辑抽样结果正确。

### 预防

- 建立字段级数据契约和Schema变更通知。
- 调度前增加必需字段存在性检查。
- 文档、DDL、实际元数据以同一版本号管理。

### 面试表述

> 本地链路验证中发现源字段版本存在`update_time/modify_time`差异。我先以实际元数据确认源字段，再在DWD统一命名并对账非空率和时间范围，没有把它描述成线上事故。

## 案例3：当前Hive不支持`TO_JSON`

### 现象

`ads_operation_com_ai_blue_2kafka`中的JSON转换查询无法通过函数解析，导致ADS不能按当前写法生成供Kafka使用的JSON。

### 证据与复现

当前SQL两次调用：

```sql
TO_JSON(MAP(...))
```

主提示词确认当前本地Hive不支持该函数。先执行最小探针，而不是直接运行整条宽表SQL：

```sql
SELECT TO_JSON(MAP('k','v'));
```

若函数不可用，问题与业务数据无关，是引擎/版本能力差异。

### 根因

SQL来自不同引擎方言或更高版本能力；当前Hive函数集与原设计不一致。把Spark SQL、Hive SQL或其他引擎的JSON函数视为通用函数，是兼容性假设错误。

### 排查

1. 用最小SQL确认函数是否注册。
2. 查询当前执行引擎和版本，而不是只看编辑器标识。
3. 检查可用函数：`SHOW FUNCTIONS LIKE '*json*'`。
4. 分开验证MAP构造、内层JSON、外层JSON，定位失败层。

### 修复

优先方案是切换到项目实际支持的Spark SQL JSON函数或平台原生JSON序列化能力。若只能使用Hive，不手工盲拼字符串；应选择经过验证的结构体/JSON UDF或在Kafka推送组件中序列化。

若必须字符串拼接，需要统一转义函数，并覆盖所有特殊字符，但其维护风险高于原生序列化。

### 验证

- 最小JSON函数探针通过。
- 生成结果可以被标准JSON解析器反序列化。
- `data`是嵌套对象而不是被二次转义的字符串。
- NULL、中文、引号、换行和反斜杠样本全部通过。

### 预防

- 开发前建立引擎版本与函数兼容清单。
- SQL评审禁止把其他引擎函数无验证地复制到Hive。
- JSON供数增加结构化契约测试。

### 面试表述

> 本地执行环境不支持原SQL里的`TO_JSON`。我先用最小函数探针确认是引擎能力问题，再选择实际引擎支持的结构化序列化方式，并用JSON解析器验证，而不是手工拼接后只看字符串外观。

## 案例4：`tag_result`枚举`only`与`only_fans`不一致

### 现象

源审核结果为“仅粉丝可见”时，DWD通过通用枚举维表关联不到中文名称，`tag_result_name`变为NULL；下游按名称统计时会漏计。

### 证据与复现

- ODS注释：`only_fans`。
- `dim_code_desc`：`only` → 仅粉丝可见。

```sql
SELECT tag_result, COUNT(*)
FROM ods_community_community_audit_result_df
WHERE pt='${bizdate}'
GROUP BY tag_result;

SELECT t0.tag_result
FROM ods_community_community_audit_result_df t0
LEFT JOIN dim_code_desc t1
  ON t0.tag_result=t1.code
 AND t1.fields_name='tag_result'
WHERE t0.pt='${bizdate}' AND t1.code IS NULL;
```

### 根因

枚举值发生过命名变更，但源系统、维表和文档没有同步；又因为DWD使用LEFT JOIN，任务不会报错，只会静默产生NULL。

### 排查

1. 统计源枚举TopN和未匹配率。
2. 查看`only`和`only_fans`是否同时存在、各自时间范围。
3. 与业务确认两者是否同义，不能仅凭中文注释合并。
4. 追踪NULL名称对ADS的影响。

### 修复

确认同义后，在维表按真实源值补齐`only_fans`；如需兼容历史值，可同时保留`only`并记录生效时间。不要只在某张DWD中临时写CASE WHEN掩盖维表缺口。

### 验证

- `tag_result`未匹配率归零或降至批准阈值。
- “仅粉丝可见”样本可正确落入限制/拦截类别。
- 历史`only`记录未被误改。

### 预防

- 每日监控枚举未匹配数量和比例。
- 新枚举先更新维表再上线源系统。
- 通用枚举表增加复合主键唯一和生效版本。

### 面试表述

> 本地对账发现源值`only_fans`与维表`only`不一致，LEFT JOIN不会报错但会静默丢名称。我通过未匹配枚举清单定位，确认业务语义后在维表统一治理，而不是在下游指标里补丁式处理。

## 案例5：前置审核标签编码与标签维表不一致

### 现象

源审核表有标签，但拆分后的`tag_code`无法关联`dim_com_audit_tag_df`；人审标签子查询使用INNER JOIN，最终DWM输入表可能大幅减少甚至整批为0。

### 证据与复现

当前DWM路径：

```text
audit.tag_code → SPLIT/EXPLODE → dim_audit_tag.tag_code
→ INNER JOIN聚合t5 → INNER JOIN主表
```

按层计数即可定位：

```sql
SELECT COUNT(DISTINCT biz_id) FROM audit WHERE pt='${bizdate}';
SELECT COUNT(DISTINCT biz_id) FROM exploded_tag;
SELECT COUNT(DISTINCT biz_id) FROM matched_tag;
```

### 根因

前置造数/源系统使用的标签码与标签维表编码体系不一致，或维表分区未到达。由于两层INNER JOIN，未匹配不仅使名称为空，还会删除整条业务记录。

### 排查

1. 查看维表目标分区是否存在、行数是否正常。
2. 比较源标签类型、前后空格、前导零和大小写。
3. 做anti join列出未匹配code。
4. 分别统计拆分前、拆分后、关联后和DWM最终行数。

### 修复

- 统一标签编码数据契约和本地造数。
- 维表分区必须先于DWM产出。
- 若业务允许无标签内容保留，标签映射改LEFT JOIN，筛选条件显式放到业务规则中。
- 若业务确实要求“必须有人审标签”，保留INNER JOIN但增加匹配率阻断检查。

### 验证

- 标签维表关联率达到约定阈值。
- DWM保留量符合业务筛选预期。
- 抽样`tag_code → tag_name`正确。
- 无法映射的标签进入异常清单而非静默消失。

### 预防

- 建立标签编码契约和维表到达依赖。
- DWM任务前置检查维表分区与标签覆盖率。
- 本地造数从维表抽取合法code，避免手工编造。

### 面试表述

> 本地DWM无数据时，我没有直接改JOIN，而是逐层统计标签拆分、维表匹配和最终保留量，确认标签编码体系不一致且INNER JOIN放大了影响，再根据业务是否强制要求人审标签选择修复方案。

## 案例6：趋势表类目编码与类目维表编码体系不一致

### 现象

DWM输入仍有动态行，但一级、二级、三级类目名称为空；如果后续按类目筛选，记录又可能被下游丢弃。

### 证据与复现

当前关联条件：

```sql
t0.level3_category_code = t1.level3_category_code
```

用anti join和匹配率验证：

```sql
SELECT
  COUNT(*) AS trend_cnt,
  COUNT(t1.level3_category_code) AS matched_cnt
FROM dwd_com_trend_detail_df t0
LEFT JOIN dim_com_trend_category_df t1
  ON t0.level3_category_code=t1.level3_category_code
 AND t1.pt='${bizdate}'
WHERE t0.pt='${bizdate}';
```

### 根因

动态表的类目字段可能是业务分类ID、审核分类ID或路径编码，而维表使用另一套类目编码；字段都叫`level3_category_code`并不能证明语义相同。

### 排查

1. 比较两侧编码格式、长度、前缀和样例。
2. 确认动态字段来源和类目维表所属系统。
3. 检查维表同一三级码是否重复。
4. 核对是否应使用`category_code`、映射桥表或有效期条件。

### 修复

- 使用同一业务编码或增加明确的跨体系映射表。
- 统一字段注释，避免把“编码”误写成“名称”。
- 维表按三级码保证唯一；若是缓慢变化维，增加有效期或快照分区条件。

### 验证

- 类目关联率和未匹配清单符合预期。
- JOIN前后行数不被重复维度放大。
- 抽样三级码及其父级名称业务正确。

### 预防

- 数据契约记录编码所属系统，不只记录字段名。
- DQC监控类目未匹配率和维表主键重复。
- 跨系统编码必须通过桥表，不做“同名即同义”假设。

### 面试表述

> 本地发现动态有值但类目名称为空。我先比较两侧编码样例和来源系统，确认是编码体系问题，而不是简单NULL，再通过统一编码或桥表解决并监控关联率。

## 案例7：DWM中内连接`t5`导致整批数据被过滤

### 现象

上游动态DWD有100条，其他LEFT JOIN也能返回数据，但生成前DWM结果为0或远小于预期。

### 证据与复现

当前`t5`是人审标签聚合子查询，并使用：

```sql
JOIN (...) t5 ON t0.trend_id=t5.biz_id
```

将SQL按JOIN顺序分段计数：主表 → 类目 → 审核 → 质检 → 机审标签 → 人审标签。若只有加入`t5`后归零，过滤边界已定位。

### 根因

INNER JOIN把“补充人审标签”同时变成“必须匹配到人审标签”的筛选条件。若标签码不匹配、维表分区为空或内容确实没有人审标签，主表记录全部被删除。

### 排查

1. 单独运行`t5`，看是否有行。
2. 检查`t5.biz_id`与`t0.trend_id`交集。
3. 继续向内检查EXPLODE结果和标签维表匹配率。
4. 与产品确认“无人审标签是否应被排除”，避免只为出数改LEFT JOIN。

### 修复

- 若标签只是补充属性：改LEFT JOIN，并将缺失标签保留为NULL/空数组。
- 若业务强制要求人审标签：保留INNER JOIN，但先修复编码/分区并增加最小保留率校验。
- 将筛选条件写成显式业务规则，例如`WHERE has_valid_human_tag=1`，提升可读性。

### 验证

- 主表100条到最终DWM的每一步减少量均可解释。
- 无标签内容的保留/过滤符合PRD。
- `trend_id`唯一性没有因标签聚合破坏。

### 预防

- 每个JOIN记录输入量、输出量和放大/保留比例。
- 对INNER JOIN设置最低关联率告警。
- JOIN类型必须在设计文档中说明业务理由。

### 面试表述

> 本地DWM为0时，我按JOIN顺序逐层加表，定位到`t5`内连接。随后继续检查标签子查询和业务筛选要求，而不是直接把JOIN改掉。最终根据“标签是否必需”决定LEFT还是INNER。

## 案例8：前置与后置审核复用同一`biz_id`

### 现象

审核表200条与动态/AI内容关联时出现一对多；前置标签和后置测评结果混在一起，黑白样本指标异常放大或语义错位。

### 证据与复现

本地造数设计为前置审核100条、后置审核100条。如果两批均使用原始`trend_id`作为`biz_id`，则：

```sql
SELECT biz_id, COUNT(*)
FROM audit
WHERE pt='2026-07-11'
GROUP BY biz_id
HAVING COUNT(*) > 1;
```

会出现同一业务ID多条且无法仅凭ID区分阶段。

### 根因

生成前审核对象是原始社区动态，生成后审核对象应是AI内容投放后生成的新动态。造数或链路设计错误地把两个生命周期当成同一业务对象。

### 排查

1. 分别提取原始动态ID集合和AI投放后动态ID集合。
2. 计算集合交集。
3. 按`biz_id`查看审核次数、时间、event和样本属性。
4. 检查DWM JOIN前后行数及指标重复。

### 修复

- 投放后必须使用新`trend_id`，后置审核`biz_id`指向新ID。
- 建议增加`audit_stage`区分`pre/post`，但不能用阶段字段掩盖ID复用错误。
- 清理错误本地分区后按正确ID重新造数和重跑。

### 验证

```text
前置审核.biz_id ∩ 后置审核.biz_id = 空集
```

- 前置100条与原始动态正确匹配。
- 后置100条与AI投放后内容正确匹配。
- DWM关联后无意外翻倍。

### 预防

- ID生成规则中预留不同范围/前缀用于本地测试。
- DQC每日检查前后置ID交集。
- 血缘文档明确“原始trend_id”和“投放后trend_id”。

### 面试表述

> 本地造数时我发现前后置审核复用同一批`biz_id`会让审核阶段混淆并造成一对多。我把投放后内容改为新`trend_id`，并增加集合交集检查。这个问题只描述为本地链路验证发现。

## 案例9：`INSERT OVERWRITE`覆盖原分区

### 现象

为补充一部分测试数据执行`INSERT OVERWRITE PARTITION(pt='2026-07-11')`后，分区中原有记录消失，只剩本次SELECT结果。

### 证据与复现

`OVERWRITE`语义是替换目标分区，不是追加。复现前后记录分区行数和主键集合：

```sql
SELECT COUNT(*), COUNT(DISTINCT id)
FROM target
WHERE pt='2026-07-11';
```

若本次SELECT只产生新增子集，覆盖后原集合自然丢失。

### 根因

把“幂等重算整个分区”的写法用于“局部追加/修补”。问题不是OVERWRITE本身错误，而是写入意图与SQL语义不一致。

### 排查

1. 确认目标是全分区重算还是局部补数。
2. 保存覆盖前行数、主键和关键指标快照。
3. 检查SELECT是否包含该分区的完整数据来源。
4. 检查静态/动态分区范围是否超出目标日期。

### 修复

- 全分区重算：保留OVERWRITE，但SELECT必须重建整个目标分区。
- 局部修补：先将旧分区与新数据按主键合并去重到临时表，再整体OVERWRITE回目标分区。
- 不用`INSERT INTO`草率绕过，因为会引入重复问题。

### 验证

- 覆盖前后主键集合符合预期：保留旧记录、替换变更记录、加入新记录。
- 总量、唯一性和指标对账通过。
- 只改动目标分区，其他日期不变。

### 预防

- 补数前明确“全量重算/局部修补”标签。
- 高风险覆盖先写临时表并验数。
- 调度参数限制允许覆盖的分区范围。

### 面试表述

> 本地补数时验证了`INSERT OVERWRITE`会替换整个目标分区。后来我先判断是否全分区重算；局部修补则先合并去重到临时表，再整体覆盖，避免原数据丢失。

## 案例10：`INSERT INTO`重复执行造成重复数据

### 现象

同一造数或加工SQL执行两次后，目标分区行数近似翻倍，主键重复，DWM和ADS指标随之增加。

### 证据与复现

执行前后检查：

```sql
SELECT
  COUNT(*) AS cnt,
  COUNT(DISTINCT business_key) AS distinct_cnt
FROM target
WHERE pt='2026-07-11';
```

若第二次执行后`cnt`增加而`distinct_cnt`不变，说明是重复追加。

### 根因

`INSERT INTO`只追加，不保证业务主键幂等；任务重试、手工重跑和调度补跑都会重复写入同一批数据。

### 排查

1. 确认目标表是可追加事件表还是每日快照/结果表。
2. 明确业务唯一键。
3. 比较重复记录的创建时间、批次ID和全部字段。
4. 向上追踪是否源本身重复或目标重复追加。

### 修复

- 每日快照/DWD/DWM/ADS结果优先按分区`INSERT OVERWRITE`重算。
- 必须追加时，加入批次ID并按业务键去重，或使用支持主键/upsert的下游存储。
- 清理本地重复分区时先保留唯一规则明确的一条，再重写分区。

### 验证

- 同一任务重复运行两次，目标结果完全一致。
- `COUNT(*) = COUNT(DISTINCT unique_key)`（在业务要求唯一的表上）。
- ADS指标不因重跑变化。

### 预防

- 为每张表声明写入模式和唯一键。
- 将“同参数连续运行两次结果不变”纳入上线验收。
- 任务批次和重试状态可追踪。

### 面试表述

> 本地重复执行`INSERT INTO`后发现行数翻倍。我通过总行数与唯一键数对比确认是目标端重复追加，结果表改为分区幂等重算，并把重复运行测试加入验收。

## 案例11：动态分区字段位置和配置问题

### 现象

审核DWD按`pt+event_code`写动态分区时可能出现动态分区未开启、严格模式限制、目标列数不匹配或数据写入错误分区。

### 证据与复现

当前写法依赖动态`event_code`：

```sql
PARTITION (pt='${bizdate}', event_code)
SELECT ..., event_code
```

复现重点不是记忆某条报错，而是检查两个必要条件：动态分区配置允许写入；动态分区字段位于SELECT末尾且顺序与PARTITION一致。

### 根因

SQL同时混合静态`pt`和动态`event_code`，但运行环境配置、列序或字段数量未与目标表契约同步。

### 排查

1. 查看`hive.exec.dynamic.partition`和`hive.exec.dynamic.partition.mode`。
2. 检查目标非分区列顺序。
3. 检查SELECT末尾分区字段顺序。
4. 先用少量固定event值验证，再检查生成的分区路径和行数。

### 修复

```sql
SET hive.exec.dynamic.partition=true;
SET hive.exec.dynamic.partition.mode=nonstrict;

INSERT OVERWRITE TABLE target
PARTITION (pt='${bizdate}', event_code)
SELECT col1, col2, ..., event_code
FROM source;
```

具体配置以生产平台规范为准；不能在不允许的环境擅自改全局参数。

### 验证

- 只生成预期`event_code`分区。
- 分区行数之和等于源过滤后行数。
- NULL/空`event_code`有明确处理，不产生脏默认分区。
- 重跑结果幂等。

### 预防

- SQL静态检查分区字段位置和数量。
- 监控每天新增分区数，防止异常枚举制造大量小分区。
- 分区策略评审同时考虑裁剪收益和小文件成本。

### 面试表述

> 本地动态分区验证时，我同时检查配置和列序：静态日期写在PARTITION中，动态`event_code`放在SELECT末尾，再用分区行数守恒确认没有错写。

## 案例12：BIGINT标签字段却使用`SPLIT/EXPLODE`

### 现象

DWM标签子查询对`tag_code`和`machine_tag_code`执行`SPLIT(code, ',')`，但审核DDL将两字段定义为BIGINT。严格引擎会类型报错；隐式转换也只能得到一个值，无法表达多标签。

### 证据与复现

DDL：

```sql
tag_code BIGINT,
machine_tag_code BIGINT
```

DWM：

```sql
LATERAL VIEW EXPLODE(SPLIT(tag_code, ','))
```

这是字段契约与加工逻辑的直接矛盾。

### 根因

真实源字段可能是逗号分隔字符串，但截图DDL误写为BIGINT；也可能源表只存单标签，而SQL沿用了多标签模板。没有先确认业务基数就选择了拆分逻辑。

### 排查

1. 查看实际表元数据类型。
2. 抽样原始值，判断是否含逗号、JSON数组或单个数值。
3. 统计每个`biz_id`是否存在多条标签记录，确认多标签到底按列还是按行存储。
4. 对比源系统接口/字段说明。

### 修复

- 若真实是逗号字符串：源/ODS/DWD字段统一为STRING，再SPLIT。
- 若真实是单个BIGINT：删除SPLIT/EXPLODE，直接关联维表。
- 若多标签按多行存储：按`biz_id`直接JOIN后`COLLECT_SET`，不拆字符串。
- 优先使用规范数组/关系表，不鼓励逗号字符串。

### 验证

- 标签数量守恒：拆分后的有效标签数与源语义一致。
- 无类型隐式转换异常。
- `biz_id`聚合后不因重复标签产生重复名称。
- 无法映射标签有异常清单。

### 预防

- 数据契约同时声明类型和基数：单值/多值、按列/按行。
- DDL与样例值自动一致性检查。
- 禁止对数值类型直接使用字符串拆分函数。

### 面试表述

> 本地检查发现DDL把标签写成BIGINT，但SQL按逗号字符串拆分。我没有直接CAST掩盖，而是先确认真实存储模型：单值就直接JOIN，多值字符串才改为STRING并拆分，多行标签则按业务ID聚合。

## 案例13：质检表`biz_id`与三级类目编码进行可疑关联

### 现象

DWM输入的`check_result_name`大量或全部为空；若类目编码恰好与某些业务ID字符串相同，还可能产生少量“看似成功但语义错误”的匹配。

### 证据与复现

当前条件：

```sql
t0.level3_category_code = t3.biz_id
```

左侧是三级类目编码，右侧注释是被质检对象业务ID。字段语义不同，是高风险关联。

### 根因

JOIN键选择错误，可能来自字段位置看错、截图转写或把“类目相关质检”误解成“用类目码做业务主键”。正确关系更可能通过动态`trend_id = quality.biz_id`，或审核`audit_id`连接质检。

### 排查

1. 比较两侧值域、长度、前缀和基数。
2. 分别测试`trend_id=biz_id`、`audit_id=audit_id`的关联率，但不以关联率最高直接判定正确。
3. 查看质检源表业务定义和样例。
4. 抽取匹配样本回查其审核内容，验证业务对象一致。

### 修复

与审核/质检数据契约确认后使用正确键：

- 内容质检：`trend_id = quality.biz_id`；或
- 审核记录质检：`audit.audit_id = quality.audit_id`。

如果一条审核多次质检，先确定取最新、最终结论还是保留明细。

### 验证

- 质检关联率符合业务覆盖范围，不追求盲目100%。
- 匹配样本的内容、审核和质检语义一致。
- JOIN前后动态粒度未被多次质检放大。

### 预防

- 血缘文档给每个ID标注所属实体，而非只写“业务ID”。
- JOIN评审要求同时提供字段名、实体、样例和基数。
- 建立外键关联率与一对多分布监控。

### 面试表述

> 本地发现三级类目码与质检`biz_id`关联，虽然类型都能转成字符串，但实体语义不同。我通过值域、业务定义和样本回查确认正确关系，再决定走`trend_id`还是`audit_id`。

## 案例14：多张明细表关联产生一对多数据膨胀

### 现象

DWM输出行数超过素材数，ADS中的素材数、攻击数、黑白样本数和难度累计异常增大；分子甚至可能超过按真实任务去重后的分母。

### 证据与复现

输出宽表依次按素材关联内容、任务和审核：

```text
resource 1:N content
resource 1:N attack_task
content.trend_id 1:N audit
```

若一条素材有2条内容、3个任务，每条内容有2条审核，直接JOIN可产生`2×3×2=12`行。

### 根因

宽表没有先声明唯一粒度，也没有在每个一对多分支先去重或聚合。LEFT JOIN只保证左表不丢，不保证左表不放大。

### 排查

1. 为每个键统计`COUNT(*)`分布和TopN。
2. 每增加一个JOIN记录总行数、唯一素材数、唯一任务数。
3. 定位首次出现放大的JOIN。
4. 检查重复是合法多事件还是同步重复。

```sql
SELECT resource_id, COUNT(*) cnt
FROM dwd_com_audit_ai_blue_content_df
WHERE pt='${bizdate}'
GROUP BY resource_id
HAVING COUNT(*)>1;
```

### 修复

先明确目标粒度：

- 素材级：内容、任务、审核先聚合到`resource_id`。
- 任务级：以`resource_id+attack_task_id`为唯一键。
- 审核级：再加`audit_id`。

取最终审核可使用：

```sql
ROW_NUMBER() OVER (
  PARTITION BY biz_id
  ORDER BY tag_time DESC, modify_time DESC, audit_id DESC
) = 1
```

指标仍应按明确业务ID去重，而不是依赖宽表行数。

### 验证

- 目标唯一键重复数为0。
- JOIN前后素材/任务去重数守恒。
- 四类黑白样本指标用明细抽样对账。
- 分子不超过分母。

### 预防

- 每张宽表在设计文档第一行声明粒度和唯一键。
- 上线DQC固定监控JOIN放大倍数。
- 评审每个JOIN的预期基数：1:1、1:N还是N:M。

### 面试表述

> 本地输出宽表行数变大时，我先统计每个JOIN键的基数并逐层记录行数，发现内容、任务和审核三个一对多相乘。修复不是简单`DISTINCT`，而是先定任务级或审核级粒度，再在各分支取最新或预聚合。

## 案例15：JSON正文特殊字符导致非法JSON

### 现象

普通文本样本能够推送，但正文含双引号、换行、回车、反斜杠或控制字符时，下游JSON解析失败；若`data`被二次序列化，还可能收到字符串而不是对象。

### 证据与复现

构造最小边界样本：

```text
标题：他说"测试"
正文：第一行\n第二行 C:\\tmp\\a
```

通过ADS生成JSON后，必须用标准解析器反序列化。只用字符串拼接或肉眼看输出不能证明JSON合法。

### 根因

- 引擎不支持原生JSON函数后改用手工拼接，却没有完整转义。
- 内层`data_json`已经是字符串，外层再次序列化导致双重转义。
- NULL、数组和数字全部被强制转成字符串，契约与研发预期不一致。

### 排查

1. 分别查看原始正文、内层`data`和最终外层JSON。
2. 用标准JSON解析器验证，不仅检查是否以`{}`包围。
3. 检查解析后`data`的数据类型是对象还是字符串。
4. 收集Kafka消费端失败样本并回溯业务主键，但本案例不虚构生产消费错误。

### 修复

- 优先使用当前引擎或推送组件的原生JSON序列化。
- 使用结构体/Map传递到序列化边界，避免“先转字符串再嵌套”。
- 明确字段类型、NULL策略、数组格式和字符编码。
- 若平台只接收字符串，仍由成熟JSON库统一转义。

### 验证

测试集合至少覆盖：

- 中文、emoji。
- 双引号、单引号。
- `\n`、`\r\n`、制表符。
- 单个和连续反斜杠。
- NULL、空字符串、超长正文。
- 解析后重新序列化与业务字段一致。

Kafka侧再按`trend_id`验证发送数、消费数、重复数和失败数。

### 预防

- 将JSON Schema/字段契约纳入上下游验收。
- 每次变更运行特殊字符回归集。
- 禁止业务SQL直接拼接未转义正文。
- 推送失败保留业务主键和错误分类，避免只记录整段敏感正文。

### 面试表述

> 本地JSON测试不是只看普通中文，而是专门构造引号、换行和反斜杠，再用标准解析器验证`data`仍是对象。这样能区分字符转义和二次序列化问题；我不会把它说成线上Kafka事故。

## 3. 15个案例的统一排查顺序

遇到DWM为空、行数异常或ADS指标不对时，按以下顺序可以避免随机改SQL：

1. **元数据**：目标表是否存在，字段、类型、分区是否一致。
2. **分区到达**：所有上游`${bizdate}`分区是否有数据。
3. **源量与唯一性**：每张表总量、主键数和重复数。
4. **枚举关联率**：标签、类目、处置结果未匹配率。
5. **逐层JOIN**：每加入一张表记录行数、去重主键数和放大倍数。
6. **过滤条件**：WHERE和INNER JOIN分别减少多少数据。
7. **写入语义**：OVERWRITE还是INTO，重跑是否幂等。
8. **结果契约**：JSON可解析、Kafka可去重、指标分子分母守恒。

## 4. 真实性边界总结

面试中可以说：

> 我在本地根据项目资料复现链路时，系统梳理了分区字段重复、字段契约不一致、枚举未匹配、JOIN过滤和放大、幂等写入以及JSON兼容等问题，并用行数、唯一键、关联率和边界样本验证修复思路。

不能说：

- “这些问题都在线上发生过。”
- “我处理过由这些问题引发的生产事故。”
- “修复后生产性能或业务指标提升了某个百分比。”
- “当前截图整理SQL就是最终生产代码。”
