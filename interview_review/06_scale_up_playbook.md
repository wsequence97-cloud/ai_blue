# AI 蓝军数据规模扩大应对手册

> 真实性边界：用户确认核心10张表已生产上线并稳定调度，但未提供真实生产数据量、资源配置、任务耗时或SLA。本手册将“当前项目已有”“当前材料缺失”“真实公司建议”和“当前可回答深度”分开，不能把方案性回答说成亲自处理过的生产案例。

## 1. 当前基线

| 维度 | 当前可确认 | 当前缺失 |
| --- | --- | --- |
| 链路 | ODS→DWD/DIM→DWM→ADS；生成前Kafka供数与生成后效果指标 | 完整生产调度图、SLA、失败重试配置 |
| 存储/计算 | Hive/Spark SQL风格，按`pt`分区，审核可能按`event_code`二级分区 | 文件格式实际参数、压缩、平均文件大小、集群资源 |
| 写入 | 截图SQL以`INSERT OVERWRITE`为主；用户确认任务稳定调度 | 生产最终SQL、补数平台和发布记录 |
| 质量 | 用户确认做过数据验证与下游验收；本地已形成DQC方法 | 生产DQC规则、阈值、告警和历史结果 |
| 数据量 | 本地`pt='2026-07-11'`为100/200条造数 | 生产日增量、存量、TB规模、热点分布 |

## 2. 分规模策略

### 2.1 单日10万

这是常规离线数仓规模，主要风险不是算力，而是口径、幂等和小文件。

- 同步：首次全量，后续按`modify_time`或CDC增量；保留删除标记。
- Spark/Hive：严格分区裁剪；小维表广播；不盲目增加executor。
- 模型：保持ODS/DWD/DWM/ADS；DWM先明确唯一粒度。
- 质量：行数、唯一性、非空、枚举、关联率、黑白样本守恒。
- 文件：避免一个同步任务产生大量KB级文件；按平台能力合并。
- 当前深度：可以结合本项目SQL详细回答，但不能声称生产就是10万。

### 2.2 单日1000万

重点从“能跑”转为“减少扫描和Shuffle”。

- 同步：CDC或更新时间增量，按业务主键去重；记录抽取水位。
- Join：大事实表先过滤分区和无效记录；类目、标签、枚举确认体量后广播。
- 一对多：审核、任务、内容在Join前取最新或预聚合。
- 文件：Parquet/ORC加压缩，目标文件通常控制在约128–512MB，具体按平台和查询模式调整。
- 并行度：依据输入大小和目标文件数设置，不用固定“越大越好”。
- 当前深度：能讲方法和本项目键，不能给出真实executor参数或耗时收益。

### 2.3 单日1亿

重点是大表Join、倾斜、Shuffle、稳定性和补数成本。

- 同步：CDC日志落ODS，批次水位、乱序和重复可追踪；删除通过delete事件或逻辑删除同步。
- Join：审核大表按日期和阶段裁剪；标签先聚合；必要时将前置/后置审核拆成可复用中间结果。
- 倾斜：统计`biz_id/resource_id/event_code/tag_code` TopN；热点拆分、两阶段聚合或加盐。
- Shuffle：只投影必要字段，Join前预聚合，避免宽行和大字段参与Shuffle。
- 稳定性：失败重试、超时、基线、依赖到达、数据延迟和补数优先级必须平台化。
- 当前深度：可以解释Spark UI定位路径，不能说亲自优化过1亿级任务。

### 2.4 历史累计数亿

- 按日增量维护，不每天重算全历史。
- 维表使用每日快照或SCD策略；事实表按事件日期分区。
- 近7日攻击指标只扫描必要日期范围，不能只读当天分区却声称覆盖7日。
- 历史补数按分区批次执行，临时表验数后再覆盖正式分区。
- 生命周期分层：ODS原始可较短或归档，核心DWD和指标按合规与业务需要保留。
- 当前深度：能设计增量与补数流程，真实保留周期未知。

### 2.5 TB级和十几TB级

- 避免全表COUNT、无分区Join和全历史去重。
- 统一列式存储、压缩、合理文件大小，治理小文件和超大文件。
- 评估分桶、排序、Z-Order或引擎特定布局，但不能脱离实际引擎机械套用。
- 大表Join先估算基数和输出量；广播必须受大小阈值和executor内存约束。
- 关键宽表考虑拆分低频大字段（正文、inputs、outputs），避免每次指标查询读取超宽列。
- 建立成本、耗时、Shuffle读写、溢写、失败率趋势看板。
- 当前深度：属于真实公司建议，当前没有本项目TB级证据。

## 3. 数据同步设计

### 3.1 全量初始化与每日增量

| 项目状态 | 建议 |
| --- | --- |
| 当前已有 | ODS全量快照风格、`pt`分区、DWD按日加工 |
| 当前缺失 | 实际同步工具配置、抽取水位、CDC日志和删除事件策略 |
| 公司建议 | 首次全量按主键切片；后续CDC或`modify_time`增量；每批记录起止水位、源量和目标量 |
| 回答深度 | 可解释方案，不能声称使用了未提供的具体CDC组件 |

### 3.2 删除数据

- ODS保留`is_del`及原始事件，便于追溯。
- DWD业务有效表按`is_del=0`过滤，同时对过滤量对账。
- 物理删除CDC需保留操作类型和删除前主键；否则下游永远不知道源记录已删。

### 3.3 迟到数据

- 以事件时间和处理时间双字段识别迟到。
- 每日任务回刷最近N天，N由真实迟到分布决定，而不是固定拍脑袋。
- 审核结果天然可能晚于投放；后置DWM/ADS应允许审核完成后回补原任务日期。

### 3.4 重跑、补数和幂等

- 每日结果表按目标分区`INSERT OVERWRITE`。
- 局部修补先合并到临时表，按业务键去重，再整体覆盖。
- 同参数连续运行两次，行数、主键和指标必须一致。
- Kafka供数需业务键去重、批次ID、发送状态和重试策略；仅Hive表幂等不等于Kafka消费幂等。

### 3.5 Schema变更

- 新增字段向后兼容；删除、改名、类型变更需影响分析。
- 上线前检查必需字段存在、类型一致、枚举覆盖。
- 字段契约覆盖`update_time/modify_time`、标签类型、JSON Schema等已发现风险。

## 4. Hive/Spark SQL优化

### 4.1 分区裁剪

- 每张大表显式限制`pt`。
- 近7日指标扫描真实7日范围，不能只查当天后用日期函数制造“7日”含义。
- 若按攻击时间分析，应按攻击日期裁剪，而不是素材创建日期。

### 4.2 静态与动态分区

- 静态日期：`PARTITION(pt='${bizdate}')`，适合单日调度。
- 动态事件：`PARTITION(pt='${bizdate}', event_code)`，动态字段置于SELECT末尾。
- `event_code`低基数且查询常过滤时才可能有收益；高基数或每日数据不大时会制造小分区。

### 4.3 小文件

- 先识别来源：同步并发、动态分区过多、Shuffle分区过多或频繁小批写入。
- 调整并行度、使用自适应合并、批量写入和周期Compaction。
- 以实际文件大小分布验证，不只看文件数量。

### 4.4 Join顺序和广播

- 先过滤大表，再Join。
- `dim_code_desc`、类目和标签可能适合广播，但必须先确认实际大小。
- 广播失败会造成executor OOM；不能把“维表”自动等同于“小表”。

### 4.5 Shuffle和宽字段

- Join前只选必要字段。
- 正文、图片URL、workflow inputs/outputs等低频大字段可考虑纵向拆分。
- 标签先拆分聚合再回主表，避免爆炸后的多行贯穿后续Join。

### 4.6 数据倾斜

诊断顺序：

1. Spark UI找耗时和输入量明显异常的task。
2. 查看Shuffle Read/Write、spill、GC和失败重试。
3. SQL统计Join key TopN与NULL比例。
4. 确认是热点业务值、NULL聚集还是上游重复。

治理选择：过滤无效NULL、热点单独处理、加盐拆分、两阶段聚合、广播小表、预聚合。必须针对根因选择。

### 4.7 OOM和磁盘溢写

- Driver OOM：过大collect、计划/分区元数据过多。
- Executor OOM：广播过大、单分区热点、超宽行、聚合集合过大。
- 磁盘溢写：内存不足或Shuffle规模大；先减少数据和倾斜，再考虑资源。
- 资源调大不是第一步，先看Stage与Task证据。

## 5. 模型设计复盘

### 5.1 为什么分层

- ODS：保留原貌和删除状态，便于追溯。
- DWD：统一类型、时间、枚举和有效记录。
- DIM：集中管理类目、标签和状态映射。
- DWM：按生成前/生成后主题复用关联结果。
- ADS：面向Kafka JSON和指标平台的具体消费。

### 5.2 DWM是否过宽

生成后DWM包含正文、媒体URL、工作流输入输出和审核字段。若大部分指标只用ID和状态，可拆为：

- 核心任务效果宽表。
- 内容大字段扩展表。
- 工作流运行明细/大字段表。

拆分依据是查询频率、存储成本和Join复用，而不是字段数本身。

### 5.3 前后置审核

- 当前同类审核事实表承载两个阶段。
- 必须保证两批`biz_id`不重叠。
- 建议增加`audit_stage`作为显式维度，便于质量校验和查询，但不能替代正确ID。

### 5.4 分区是否增加`event_code`

需要比较：每日量、事件数量、查询过滤率、平均分区文件数。若事件多且每分区很小，二级分区得不偿失。

### 5.5 快照、增量和拉链

- 每日全量快照：小而常变的人设/配置表，查询某日状态方便。
- 增量事实：攻击、审核、工作流运行等事件。
- 拉链：需要查询人设、标签或类目历史有效期且每日全量存储成本高时。

### 5.6 指标口径收口

- 每项指标登记业务定义、分子、分母、去重键、时间和审核阶段。
- 黑样本只用“拦截/漏过”，白样本只用“放过/误杀”，减少成功率视角歧义。
- 指标平台由统一owner评审和版本管理；本人参与口径讨论、负责SQL与维护。

## 6. 质量和稳定性

| 检查 | 本项目关键对象 | 建议规则 |
| --- | --- | --- |
| 行数波动 | ODS/DWD/DWM/ADS分区 | 同比/环比阈值按历史分布设置 |
| 主键唯一 | `trend_id/resource_id/workflow_runs_id/attack_task_id` | 目标粒度唯一键重复为0 |
| 非空 | 各类ID、样本属性、时间 | 关键键空值阻断，非关键属性告警 |
| 枚举合法 | event、tag result、sample、status | 未匹配率监控，新code告警 |
| 外键关联率 | 内容→素材/人设/工作流/审核 | 按链路分别统计，不用一个总比例掩盖问题 |
| 前置匹配率 | 原始`trend_id`→前置审核 | 解释无审核内容，防INNER JOIN静默丢失 |
| 后置匹配率 | 投放后`trend_id`→后置审核 | 区分未完成审核与关联错误 |
| ID隔离 | 前置/后置`biz_id` | 交集必须为0 |
| 黑白守恒 | 黑拦截+黑漏过+未知=黑总量；白放过+白误杀+未知=白总量 | NULL/待审核单列 |
| 分区到达 | 全部上游`pt` | 依赖未到阻断下游 |
| SLA | Kafka供数、效果指标 | 设基线、延迟告警、失败重试和人工升级路径 |

## 7. 元数据、血缘与生命周期

- 表、字段、任务、指标均登记owner、描述、更新频率和生命周期。
- 字段级血缘重点记录`trend_id/resource_id/request_id/biz_id/audit_id`。
- 变更前做下游影响分析，尤其是JSON字段大小写和指标枚举。
- 过期分区按合规和使用频率清理；生产保留周期目前未知。
