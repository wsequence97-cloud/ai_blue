## 模拟面试双视角规则（2026-07-12更新）

### 面试官视角

- 只读取候选人的简历内容和本次模拟面试中已经说出口的信息。
- 不把项目仓库、SQL、表结构、主提示词或前期审计结论当作面试官已知事实。
- 不在问题中泄露候选人尚未主动提及的正确表名、关联键、故障根因或答案方向。
- 可以基于简历声明和候选人回答中的矛盾、模糊点继续追问。

### 复盘教练视角

- 在候选人完成回答后，结合完整项目材料核对事实。
- 明确指出回答正确之处、错误、模糊点、夸大风险和最容易被追问的漏洞。
- 给出一版符合真实职责边界、技术上合理、可以用于面试的参考答案。
- 区分“材料确认的项目事实”“用户确认的个人经历”“本地复现结论”和“真实公司建议”。

### 主问题2首次反馈

#### 正确的地方

2. DWD主要负责清洗、类型转换和枚举标准化；DWM的核心价值是围绕一个确定业务粒度整合跨表主题数据并提高复用。

#### 粒度解释

粒度是“一行数据代表的最细业务对象”。例如：

- 一行一条社区动态：粒度是`trend_id`。
- 一行一个攻击任务：粒度是`attack_task_id`。
- 一行一个素材的一次攻击：粒度可写成`resource_id + attack_task_id`。

粒度决定主键、Join方式、是否会重复以及指标怎样去重。

这张DWM关联审核结果和人审标签时，为什么同一个`trend_id`可能产生多行？当前`t5`使用INNER JOIN又会造成什么影响？你会怎样同时避免数据膨胀和不合理丢数？

### 追问2反馈

#### 正确的地方

- 认识到一个业务对象可能有多次审核状态。
- 认识到一次审核可能带多个风险标签。
- 对没有把握的膨胀治理明确说不知道，没有虚构做法。

#### 需要纠正

1. “作者要求复审、修改后再上传”在当前项目材料中没有直接证据，只能作为可能场景，不能当成本项目确定流程。
2. 当前`t5`读取的是人审`tag_code`，经过`SPLIT/EXPLODE`关联审核标签维表，再按`biz_id`聚合；它没有读取`machine_tag_result`。
3. 因此`t5`的实际效果是：只保留能够匹配到人审标签的动态。它不能直接证明是在过滤“机审没通过的记录”，也不能证明内容是否真实。
4. SQL注释中的业务意图与SQL实际条件并不完全一致，面试时应指出需要与产品确认，而不是替注释补出不存在的条件。

#### 避免数据膨胀

- 多次审核：先按`biz_id`和审核时间排序，取需要的最终审核；若要保留历史，则必须把宽表粒度改为审核级。
- 多标签：`EXPLODE`后按`biz_id`使用`COLLECT_SET(tag_name)`聚回一行，避免重复标签。
- 每一步检查`COUNT(*)`、`COUNT(DISTINCT trend_id)`和Join放大倍数。

示意思路：

```sql
ROW_NUMBER() OVER (
  PARTITION BY biz_id
  ORDER BY tag_time DESC, modify_time DESC, audit_id DESC
) AS rn
```

取`rn=1`得到最终审核，再与标签聚合结果关联。

#### 避免不合理丢数

- 如果人审标签只是补充属性，主表与`t5`应使用LEFT JOIN，无标签内容保留为空。
- 如果业务明确要求只有具备有效人审标签的内容才能送模型，可以保留INNER JOIN，但需要把规则写成显式资格条件，并监控保留率。
- 不能为了让任务出数就盲目把INNER改LEFT，也不能只因为注释写了“一定要JOIN”就不验证业务规则。

### 追问3反馈

- LEFT/INNER JOIN的选择已经回答正确，并且能把SQL行为与业务资格条件分开。
- “行转列”只能把不同审核类型或阶段展开成字段，不能自动解决同一类型存在多次审核的问题。
- 多次审核仍需先定义最终状态，例如按`tag_time、modify_time、audit_id`降序取`ROW_NUMBER=1`。
- 多个标签仍需在拆分和维表映射后按`biz_id`使用`COLLECT_SET`聚合，才能回到一行一个`trend_id`。

### 第2轮追问4

如果同一个`biz_id`先后有“隐藏、复审通过、再次隐藏”三条人审记录，你会依据哪些字段确定最终审核记录？为什么不能只使用`MAX(tag_result)`或简单`DISTINCT`？

**候选人回答：**

> 这个情况我不知道怎么说。给出MAX或者DISTINCT只能给出其中的一条，我认为这个要看业务需要的是什么，需要最新的话就直接用最新的数据覆盖，其他的我不知道怎么回答。

### 追问4复盘教练点评

#### 回答正确的地方

- 首先确认业务需要“最终状态”还是“完整审核历史”，这是正确的建模前提。
- 知道如果业务要最终状态，应选择最新记录，而不是保留全部记录到动态粒度宽表。
- 对不了解的实现没有继续编造，可信度较好。

#### 回答中的问题

1. `MAX(tag_result)`不是“随机拿一条”，而是按字符串/编码排序取最大值；它与审核发生时间没有必然关系。例如`pass`在字符排序上大于或小于`hide`，都不能代表最终状态。
2. `DISTINCT`只删除所有选择字段完全相同的重复行。三条审核的时间、结果或审核ID不同，`DISTINCT`会全部保留。
3. “用最新数据覆盖”只是目标，没有说明如何稳定判断最新。如果两条记录`tag_time`相同，还需要稳定的第二、第三排序字段。
4. 若直接覆盖且不保留审核明细，会失去审核过程追溯能力。合理做法通常是DWD保留审核明细，DWM按消费需求取最终状态。

#### 合理参考答案

> 我会先确认下游要审核历史还是最终审核状态。如果DWD需要保留过程，我会保留每一条审核记录；生成前DWM目标是一行一个内容，因此在进入DWM前按`biz_id`分组，用`ROW_NUMBER`按`tag_time`降序取最新一条。如果`tag_time`可能相同，再按`modify_time`和`audit_id`降序做稳定排序，取`rn=1`。不能直接用`MAX(tag_result)`，因为审核结果编码的大小与发生先后无关；也不能用`DISTINCT`，因为不同时间、不同结果的记录并不重复，仍会保留多行。如果业务需要同时分析首次和最终审核，我会分别计算首次状态和最终状态两个字段，而不是丢掉历史。

```sql
SELECT *
FROM (
  SELECT
    t.*,
    ROW_NUMBER() OVER (
      PARTITION BY biz_id
      ORDER BY tag_time DESC, modify_time DESC, audit_id DESC
    ) AS rn
  FROM dwd_com_audit_detail_df t
  WHERE pt='${bizdate}'
) s
WHERE rn=1;
```

### 主问题3复盘教练点评

#### 正确的地方

#### 错误或模糊点

1. 生成后DWM当前以素材为主线，不能直接说“一行一条AI动态”。在未治理一对多前，实际可能是一条素材关联内容、任务、审核后的组合行；生产设计应明确素材级、任务级或审核级粒度。
2. 素材与内容的关联是：`resource.resource_id = content.resource_id`，不是连接内容表的`id`。
3. 素材不能用`resource_id`直接关联审核表`id`。审核关系是：`content.trend_id = audit.biz_id`。

5. 素材关联攻击任务使用`resource.resource_id = user_attack.resource_id`，不是内容表的`biz_id`。
6. 内容关联工作流使用`content.ai_blue_content_request_id = workflow.workflow_runs_id`。
7. 回答遗漏了实际攻击账号`user_id`与AI人设用户`ai_blue_user_id`的语义差异。

#### 合理参考答案

> 两张DWM要拆开，是因为它们位于不同生命周期、粒度也不同。input DWM位于生成前，以原始社区动态`trend_id`为主线，向Kafka和大模型提供正文、作者、类目、标签、审核和质检上下文；output DWM位于生成、投放和审核之后，以素材`resource_id`为主线，回收生成内容、人设、攻击任务、工作流运行和审核结果，用于效果指标。生成后宽表要先明确粒度，如果按一次素材投放来分析，我会把目标粒度定义为`resource_id + attack_task_id`；若还要保留每次审核，再增加`audit_id`。关联上，素材和内容通过两边的`resource_id`连接，内容和AI人设通过`ai_blue_user_id`连接，素材和攻击任务通过`resource_id`连接，内容请求通过`ai_blue_content_request_id = workflow_runs_id`连接，投放后的内容通过`trend_id = audit.biz_id`回收审核结果。实际攻击账号`user_id`与AI人设用户不是同一个概念。
