# AI 蓝军项目面试陈述与高频问答

## 1. 面试讲解原则

1. 先讲业务闭环，再讲数仓分层，不要上来报表名。
2. 黑白样本结果使用“拦截、漏过、放过、误伤”，避免成功率视角混乱。
3. 明确本人负责离线数仓和指标，Dify、审核策略、蓝军平台是协同上下游。
4. 所有表都要能说出粒度、主键、来源、下游和为什么需要。
5. 简历数字要保持一致：核心 DWD 6、DWM 2、ADS 2、PRD 指标类别 17。
6. 遇到截图 SQL 的风险，区分“原始代码现状”和“生产上应如何治理”。

## 2. 30 秒项目介绍

> 这个项目是小红书社区风控 AI 蓝军数据资产建设。业务通过大模型生成更真实的黑白样本和用户人设，再自动投放到审核链路，测试机审、人审对违规内容的漏过和对正常内容的误伤。我负责离线数仓部分：把社区帖子、审核标签和质检数据加工成 Dify 输入，再把生成内容、素材、人设、攻击任务、工作流和审核结果关联回来，建设核心 DWD 6 张、DWM 2 张、ADS 2 张和蓝军效果指标，支撑攻防大盘和策略复盘。

## 3. 1 分钟项目介绍

> 项目背景是蓝军样本收集大量依赖人工，约占运营人力的 50%，同时已有攻击内容较生硬、用户无人设，不能很好模拟真实社区行为。项目通过数据开发、Dify 和蓝军/审核系统协作形成两个闭环：第一个是生成闭环，我把历史社区帖子、作者互动、三级类目、机审、人审标签和质检结果清洗后形成 DWM 输入宽表，再封装 JSON 给 Dify；第二个是测评闭环，Dify 生成内容和人设后进入蓝军素材库，蓝军平台创建任务并投放，审核平台返回机审、人审结果，我再关联素材、内容、人设、任务和 workflow_runs 形成 DWM 输出宽表，最后统计黑白样本拦截、漏过、放过、误伤、复投、相似度和难度等指标。我的核心职责是离线数据资产、关联链路和指标口径，Dify 工作流和审核策略由对应团队实现。

## 4. 3 分钟完整陈述

> 这个项目服务社区风控攻防测评。黑样本是应该被拦截的风险内容，用来测试审核漏过；白样本是应该正常放过的合规内容，用来测试误伤。原来的痛点是黑白样本主要依赖人工收集，样本收集约占 50% 运营人力，而且内容不符合社区调性、模拟用户没有稳定人设。
>
> 项目方案由四部分组成：历史社区和审核数据、Dify 生成、蓝军任务投放、审核结果回收。我的职责是把这四部分通过离线数仓连接起来。
>
> 生成前，我从社区动态、审核结果、质检、审核标签和三级类目数据出发，在 DWD 统一字段、时间和枚举；DWM 输入表以 `trend_id` 为核心，补充作者、互动、类目、机审、人审标签和质检结果，再由 ADS 转成约定 JSON 支撑 Dify。Dify 内部会做分词、高亮提取、Prompt 组装、文生文、文生图和用户人设生成，这部分我负责接口和数据支撑，不负责模型实现。
>
> 生成后，蓝军系统沉淀人设、内容、素材和攻击任务四类数据。我在 DWD 清洗这些业务表，同时接入 Dify workflow_runs 和审核结果。DWM 输出表以 `resource_id` 为主线，通过内容表关联 `trend_id`、`ai_blue_user_id` 和工作流请求 ID，再关联攻击任务及机审、人审结果，形成生成到审核的全链路明细。ADS 再按日期和内容类型聚合素材、攻击、复投、黑白样本机审和人审效果等指标。
>
> 项目核心交付口径是 DWD 6 张，包括工作流 1 张、审核 1 张和蓝军业务 4 张；DWM 2 张分别服务生成前和生成后；ADS 2 张分别服务 JSON 供数和效果大盘。PRD 有 17 类业务指标，一类指标可能拆成多个物理字段，所以 ADS DDL 中实际有 25 个字段。项目整体降低了运营投入并提高了有效黑白样本产出，我的数据链路主要支撑生成、投放效果评估和策略复盘。

## 5. STAR 结构复盘

### S：Situation

- 黑白样本人工收集成本高。
- 攻击内容和用户不够真实。
- 生成、投放、审核和效果分析没有统一数据链路。

### T：Task

- 建立 Dify 前置供数。
- 打通蓝军业务、Dify 工作流和审核结果。
- 建立可复用明细宽表和攻防指标。
- 对齐字段、枚举、JSON 和指标口径。

### A：Action

- 枚举数据源和表间关联，申请源数据。
- 建设核心 DWD 明细和通用维度映射。
- 设计生成前、生成后两张 DWM 宽表。
- 设计 JSON 结构和 ADS 指标。
- 进行行数、枚举、外键、重复和指标对账。
- 与 AI 产品、策略、后端和审核团队确认边界。

### R：Result

- 核心 DWD 6 张、DWM 2 张、ADS 2 张。
- 支撑 PRD 17 类指标和蓝军效果大盘。
- 支撑项目整体降低运营投入、增加有效黑白样本并暴露审核薄弱点。

业务结果属于项目整体产出，不要全部归因为个人 SQL。

## 6. 业务类高频追问

### Q1：什么是蓝军？

蓝军模拟黑产或风险攻击，主动投放测试内容，观察风控系统能否正确拦截。项目同时投放白样本，检查审核是否对正常内容产生误伤。

### Q2：为什么黑样本和白样本都需要？

只测黑样本只能发现漏过，不能发现规则过严。黑样本验证召回风险内容的能力，白样本验证正常内容的通过能力，两者共同反映审核准确性。

### Q3：攻击成功是什么意思？

需要先说明视角。黑样本通过代表蓝军攻击成功、风控漏过；白样本被拒绝代表蓝军发现误伤。为了避免歧义，我会直接使用黑拦截、黑漏过、白放过、白误伤。

### Q4：为什么要用大模型？

不是为了替代审核，而是为了降低样本生产成本并提高仿真度。大模型可以根据真实社区内容、人设、类目和风险标签生成更多变体，使内容更接近真实用户表达。

### Q5：为什么还要历史审核数据？

只给模型正文无法知道哪些内容具有风险语义、审核结果是什么。审核标签、机审、人审和质检结果为模型提供风险方向和质量反馈，也能用于筛选高质量参考内容。

### Q6：项目怎样形成闭环？

历史数据支撑生成，生成素材进入蓝军任务，审核平台返回结果，数仓统计漏过和误伤，再用于补充样本、调整难度和优化策略，形成下一轮生成和攻击。

## 7. 数仓建模类高频追问

### Q7：为什么使用 ODS、DWD、DWM、ADS 分层？

- ODS 保留源系统原貌，便于追溯。
- DWD 统一类型、枚举、删除和时间口径。
- DIM 提供统一类目和标签名称。
- DWM 以业务主题拼接复用宽表，避免下游重复 JOIN。
- ADS 面向具体 JSON 接口和指标消费。

### Q8：为什么有两张 DWM？

生命周期和粒度不同。输入表在生成前，以社区帖子 `trend_id` 为核心；输出表在生成后，以素材 `resource_id` 为核心，还包含人设、任务、工作流和审核结果。强行合并会造成粒度混乱和大量空字段。

### Q9：DWM 输入表的主表是什么？

`dwd_com_trend_detail_df`。它代表当日社区帖子，再 LEFT JOIN 类目、审核、质检和机审标签；人审标签使用 INNER JOIN，因此没有可映射人审标签的帖子会被过滤。

### Q10：DWM 输出表的主表是什么？

`dwd_com_audit_ai_blue_resource_df`。它保留所有有效素材，再依次 LEFT JOIN 生成内容、人设、攻击任务、workflow_runs 和审核结果。

### Q11：最重要的关联键有哪些？

- `trend_id=biz_id`：内容与审核。
- `resource_id`：素材、内容和攻击任务。
- `ai_blue_user_id`：生成内容与用户人设。
- `ai_blue_content_request_id=workflow_runs_id`：生成内容与 Dify 运行。
- `attack_task_id`：攻击任务追踪。

### Q12：AI 用户和实际攻击用户有什么区别？

`ai_blue_user_id` 表示内容使用的 AI 人设用户；攻击关系表中的 `user_id` 表示实际执行投放的运营账号。两者可能关联但语义不同。

### Q13：DWD 6 张具体是哪 6 张？

工作流运行 1 张、审核结果 1 张、人设/内容/素材/攻击 4 张。社区动态和质检明细是生成前供数依赖或复用表，单独说明，不计入简历核心 6 张。

### Q14：为什么使用通用枚举维表？

把事件、内容类型、审核处置、样本属性和人设状态等 code 统一映射为 name，避免每张表重复写 CASE WHEN，也便于集中维护和监控未匹配枚举。

## 8. SQL 类高频追问

### Q15：标签列表怎样加工？

先对逗号分隔的 `tag_code` 或 `machine_tag_code` 使用 `SPLIT`，再 `LATERAL VIEW EXPLODE` 转成多行，关联审核标签维表获得中文名，最后按 `biz_id` 使用 `COLLECT_LIST` 聚合。

### Q16：为什么标签关联一个用 LEFT JOIN、一个用 INNER JOIN？

机审标签 LEFT JOIN 可以保留没有机审标签的内容；人审标签 INNER JOIN 会把没有可映射人审标签的内容过滤。当前 SQL 注释表示需要参考人审数据，但是否应该强制过滤需要与产品确认。

### Q17：怎样处理逻辑删除？

社区帖子、素材和攻击关系 DWD 使用 `is_del=0`。审核 ODS 也有 `is_del`，但当前截图 DWD 审核 SQL 没有过滤，这是需要补充核对的数据质量点。

### Q18：工作流时间为什么加 28800？

意图是把 UTC 转为东八区时间。上线前必须确认源时间是否确实为 UTC，否则可能重复偏移。

### Q19：怎样从工作流找到业务内容？

内容表的 `request_id` 标准化为 `ai_blue_content_request_id`，与 `workflow_runs_id` 关联；工作流表还从输入 JSON 的 `$.id` 提取 `biz_id` 作为辅助业务键。

### Q20：当前 SQL 最大的粒度风险是什么？

输出宽表同时 JOIN 内容、攻击任务和审核三个一对多关系，可能形成乘积，导致下游 COUNT/SUM 放大。需要先定义唯一粒度，再对各子表取最新、聚合或在指标端去重。

## 9. 指标类高频追问

### Q21：简历 17 个指标为什么 ADS 有 25 列？

17 是 PRD 的业务指标类别；一个类别可能拆成黑/白、机审/人审、成功/失败多个字段。ADS 25 列是物理字段数量，两者不是同一统计层级。

### Q22：黑样本机审漏过如何计算？

分子是 `sample_code=0` 且机审结果为 `init/pass` 的攻击任务数；分母是黑样本攻击总数。若计算率，还要明确首投/复投、是否去重和时间范围。

### Q23：白样本误伤如何计算？

分子是 `sample_code=1` 且审核结果非 `init/pass` 的样本数；分母可按全部白样本或转人工白样本，必须根据 PRD 最终定义确认。

### Q24：机审直接处置率怎样计算？

机审未转人工且直接给出最终处置的样本数除以黑白样本总数。实现时需要使用 `is_manual` 区分是否转人工，不能只看机审结果字段。

### Q25：机审直接处置错误率怎样计算？

在机审直接处置样本中，黑样本被直接通过和白样本被直接拒绝的数量，除以机审直接处置总量。

### Q26：一本多投成功率怎样算？

先用 `is_used=1` 或同一 `resource_id` 多任务识别复投，再根据样本属性判断结果。黑样本复投成功通常指再次漏过；PRD 或 ADS 中也可能按“拦截成功”命名，所以必须先确定视角。

### Q27：为什么当前 ADS 不能完全代表 PRD 17 类指标？

现有 SQL 能直接支持规模、黑白样本结果和复投等；防御质量分、普通与 AI 对照、设备/IP/轨迹仿真、标签覆盖和人设排行榜没有在当前 ADS 查询中完整体现，需要其他数据集或后续计算。

## 10. 性能和稳定性追问

### Q28：怎样优化这条 Spark SQL 链路？

- 所有表按 `${bizdate}` 分区裁剪。
- 类目、标签、枚举等小维表可广播，但需确认实际大小。
- 在 JOIN 前对审核、任务等一对多表去重或聚合。
- 避免重复扫描审核大表，可复用中间结果。
- 对 `resource_id/trend_id/biz_id` 的倾斜进行频次分析，必要时热点拆分或加盐。
- 只选择下游需要的字段，减少宽表 shuffle 和存储。

### Q29：如何判断发生数据倾斜？

观察 Spark UI 某些 task 的输入量和耗时显著高于其他 task，再统计 JOIN key 的 topN 分布。审核场景或热点素材可能造成 `biz_id/resource_id` 倾斜。

### Q30：为什么 DWD 审核按 event_code 分区？

审核数据量大且场景多，按日期＋事件场景可以减少特定场景查询扫描。但要避免小分区过多，并保证 DDL 不重复声明普通列和分区列。

### Q31：怎样保证任务可重跑？

按业务日期使用 `INSERT OVERWRITE PARTITION`，保证同一分区幂等；同时冻结维表分区、控制动态分区、记录调度参数，并在重跑后执行行数和指标对账。

### Q32：7 日指标如何实现？

当前 ADS 子查询按 `resource_id` 统计满足日期差小于等于 7 的攻击任务数。生产上还应明确下界、分区扫描范围、攻击时间字段和是否包含当天。

## 11. 数据质量追问

### Q33：上线前做哪些校验？

ODS/DWD 行数对账、删除量核对、主键重复、枚举未匹配率、时间范围、关键外键空值、JOIN 放大倍数、黑白样本人工抽样以及 ADS 分子分母校验。

### Q34：如何监控枚举变化？

统计 code 无法关联 `dim_code_desc` 的数量和比例，出现新 code 时告警并推动补充映射，避免中文名称为空导致指标丢失。

### Q35：如何验证黑白指标没有写反？

构造四条最小样本：黑通过、黑拒绝、白通过、白拒绝，分别验证它们只落入黑漏过、黑拦截、白放过、白误伤中的一个分支。

### Q36：NULL 审核结果怎么处理？

SQL 的 `NOT IN` 遇到 NULL 不会返回 true，因此缺少审核结果的记录不会进入成功或失败。应单独定义“未完成/未知”状态，不直接塞入成功或失败。

## 12. 协作和项目负责人追问

### Q37：你与 AI 产品怎样协作？

确认模型需要的字段、样本筛选、三级类目、审核标签和 JSON 格式；确认生成结果如何回写以及 workflow_runs、request_id 的关联规则；对无法关联和异常状态定义兜底。

### Q38：你与策略团队怎样协作？

确认黑白样本、首投/复投、机审/人审、通过/拒绝的业务方向，以及每个指标的分子、分母、时间字段和去重键。

### Q39：你与后端怎样协作？

确认蓝军四张源表的主键、状态、逻辑删除、任务和素材关系，确认 JSON 消费方式、结果回写字段和上线时间表。

### Q40：项目中最大的挑战是什么？

不是单表开发，而是跨系统 ID 和口径统一：社区内容用 `trend_id`，蓝军素材用 `resource_id`，人设用用户 ID，Dify 用 request/workflow ID，审核用 `biz_id`。需要建立映射链路，并防止一对多 JOIN 放大指标。

### Q41：如果重新做一次，会改进什么？

- 在设计阶段先明确输入表和输出表的唯一粒度。
- 建立字段级数据契约和主键基数文档。
- 将审核最新状态、标签聚合和任务关系做成可复用中间层。
- 对 ADS 使用明确的攻击时间或审核完成时间。
- 为黑白样本四种结果编写自动化数据测试。
- 将 Kafka 写入、Dify 回写和数仓任务纳入统一链路监控。

## 13. Dify 边界回答

### 面试官问：Dify 是你搭的吗？

> 不是。我了解它的输入、预处理、分词、高亮、Prompt、文生文/图/用户和出参流程，负责与 AI 团队对齐输入 JSON、请求 ID 和结果字段，并在数仓中记录 workflow_runs 做效果追踪。工作流节点和模型由 AI/研发团队实现。

### 面试官问：Kafka 是你写的吗？

> 当前我负责的是 ADS JSON 数据结构和供数结果。现有 SQL没有 Kafka Producer 代码，所以我不会把 Kafka 写入程序描述为本人实现；如果生产调度由平台配置，我会按实际参与范围说明。

### 面试官问：审核策略是你优化的吗？

> 我负责提供机审、人审、漏过和误伤数据以及指标分析，帮助策略定位问题；规则、模型和人审策略的最终调整由策略和审核团队负责。
