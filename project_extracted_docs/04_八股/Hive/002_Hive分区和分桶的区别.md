# Hive分区和分桶的区别

## 一、面试主答

1. 分区和分桶都是物理组织数据的方式，但解决的问题不同：分区主要减少扫描范围，分桶主要让数据按某个Key形成稳定布局。
2. 分区按字段实际取值建立目录，例如按`pt`分区。查询带分区条件时，Hive可直接跳过无关目录，所以适合日期、小时等常用过滤字段。
3. 分桶是在分区内部按字段哈希写入固定数量的桶文件。普通Join即使不分桶，也会在运行时Shuffle保证相同Key汇集；若两张大表长期按同一Key且采用兼容桶规则，才可能利用桶布局减少重复重分发。
4. 选型时，先看是否需要分区裁剪，再看是否存在稳定、反复的大表关联或抽样需求。分桶不是默认操作，也不保证均匀，热点Key仍可能造成倾斜。

## 二、关键流程或代码

| 对比项 | 分区 | 分桶 |
| --- | --- | --- |
| 组织规则 | 按字段实际值建目录 | 按字段哈希写固定桶文件 |
| 主要收益 | 分区裁剪，少扫目录 | 稳定数据布局，可能减少重复Shuffle |
| 常见字段 | `pt`、小时、地区 | 高频Join的高基数Key |
| 使用边界 | 分区过细会产生大量目录和小文件 | 两表桶键或规则不兼容时仍需Shuffle |

## 三、本次讨论后的复盘结论

- **我原来容易混淆的点：** 曾把分桶理解成任务运行时默认的哈希分区，并认为桶数就是Reduce数。
- **修正后的理解：** 运行时Shuffle负责本次任务把同Key汇集；Hive分桶是预先持久化的数据布局，两者不是一回事。
- **以后判断问题的标准：** 先问是在优化目录扫描，还是在复用长期稳定的Key布局；再核对桶键、桶数及写桶规则是否兼容。
- **一句话记忆：** 分区先少读目录，分桶再预排Key。

## 四、高频追问

### 追问1：不分桶，相同Join Key也会到一起吗？

会。执行引擎会按Join Key进行Shuffle，使相同Key进入同一处理分区。分桶不决定Join正确性，它提供的是可复用的物理布局，满足条件时才有机会减少运行时重分发。

### 追问2：桶数等于Reduce数吗？

不等于。桶数是表的长期存储属性，Reduce数是某次任务的运行并行度。写入分桶表时执行计划需要保证数据正确落桶，但不能把两个概念直接画等号。

### 追问3：什么场景值得分桶？

更适合数据量较大、长期反复按同一高基数Key关联或抽样的表。一次性任务、低基数热点字段，或关联方式经常变化时，维护桶布局的成本可能高于收益。

## 五、项目或开发场景映射

- **通用开发场景：** 订单表按日期分区以裁剪历史数据；若两张大表长期按`user_id`关联，再评估按该字段兼容分桶。
- **本项目可真实使用的表述：** ODS与DWD蓝军内容表均按`pt`分区，DWD SQL通过`WHERE t0.pt='${bizdate}'`读取当天数据；现有建表SQL未声明分桶。
- **不能过度表述的部分：** 不能声称项目已按`resource_id`分桶，或已经通过桶Join取得性能收益；这些只能作为后续评估思路。
