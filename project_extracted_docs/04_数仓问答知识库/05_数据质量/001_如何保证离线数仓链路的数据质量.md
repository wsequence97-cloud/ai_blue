# 如何保证离线数仓链路的数据质量

## 1. 原问题

如何保证 AI 蓝军项目从 ODS、DWD、DIM、DWM 到 ADS 这条离线数仓链路的数据质量？

## 2. 核心结论

不能只在 ADS 最后检查一次行数，而要建立“口径定义—分层校验—质量门禁—指标对账—告警补数”的完整闭环：

1. 建模前明确每张表的业务粒度、唯一键和统计时间口径。
2. ODS 到 DWD 校验分区、主键、空值、逻辑删除、枚举和时间转换。
3. DWD 到 DWM 重点检查关联基数、外键缺失和多个一对多 JOIN 的行数放大。
4. DWM 到 ADS 使用黑拦截、黑漏过、白放过、白误伤四类最小样本验证指标。
5. 将核心规则配置为强 DQC，失败时阻断下游并告警；修复后按业务分区覆盖重跑。

## 3. 完整解释

### 3.1 先定义粒度和唯一键

质量检查必须以粒度为前提。没有先说明“一行代表什么”，就无法判断重复数据和聚合结果是否正确。

| 表或对象 | 建议粒度或唯一键 |
| --- | --- |
| 社区动态 DWD | `trend_id` |
| 审核明细 DWD | `audit_id`；需要最终状态时可按 `biz_id + event_code` 取最新记录 |
| 质检明细 DWD | `check_id` |
| 蓝军素材 DWD | `resource_id` |
| 蓝军生成内容 DWD | `ai_blue_content_task_id` 或 `trend_id` |
| 蓝军攻击关系 DWD | `resource_id + attack_task_id + user_id` |
| Dify 工作流 DWD | `workflow_runs_id` |
| DWM 输入宽表 | 每日一条 `trend_id` 及其审核上下文 |
| DWM 输出宽表 | 建议明确到 `resource_id + trend_id + attack_task_id`；保留多次审核时增加 `audit_id` |
| ADS 大盘 | `date_id + ai_blue_content_type_name` |

还要确认多版本语义：一条素材多次生成、多次投放、多次审核时，是保留全部事件，还是只保留最新状态。不同选择会直接改变 DWM 粒度和 ADS 分母。

### 3.2 ODS 到 DWD：源数据和清洗结果对账

这一层需要检查：

- 当天分区是否存在、是否为空、产出是否准时。
- 行数与历史同期相比是否异常波动。
- 主键是否为空或重复。
- 必填字段空值率是否超过阈值。
- `is_del=0` 的有效行数是否与 DWD 保留行数一致。
- 枚举 code 是否都能匹配 `dim_code_desc`。
- 毫秒时间戳、字符串时间和时区转换是否正确。
- ODS Schema 是否发生字段新增、删除、改名或类型变化。
- DDL 与 INSERT SELECT 的列数、顺序和类型是否一致。

建议区分两类规则：

- 强规则：分区缺失、行数为零、主键重复、核心字段为空、DDL 与 SELECT 列错位。触发后阻断下游。
- 弱规则：行数轻微波动、非核心字段空值率上升、少量枚举未映射。触发告警并继续观察。

### 3.3 DWD 到 DWM：控制 JOIN 放大和数据丢失

AI 蓝军输出宽表同时关联素材、生成内容、用户人设、攻击任务、工作流和审核结果。多个一对多关系同时出现时会形成乘积：

```text
1 个素材
× 2 条生成内容
× 3 个攻击任务
× 每条内容 2 条审核记录
= 12 行输出
```

因此需要：

1. JOIN 前统计每个关联键的基数，例如每个 `resource_id` 对应多少内容和任务。
2. JOIN 后记录总行数、去重键数量和相对主表的放大倍数。
3. 按业务决定取最新记录、保留任务级明细或保留审核级明细。
4. 监控内容找不到素材、人设、工作流或审核记录的比例。
5. 标签拆分前后检查数量，以及无法关联标签维表的 code 比例。
6. 对 INNER JOIN 记录过滤前后行数，区分业务筛选和异常丢数。

### 3.4 DWM 到 ADS：按业务真值表验证指标

蓝军效果不能笼统地只说成功或失败，应明确防守视角：

| 样本类型 | 审核正确 | 审核错误 |
| --- | --- | --- |
| 黑样本 | 被拦截 | 被放过，即漏过 |
| 白样本 | 被放过 | 被拦截，即误伤 |

至少构造四条最小测试数据，分别覆盖黑拦截、黑漏过、白放过和白误伤，再人工核对机审、人审及 ADS 字段。

还要验证以下关系：

```text
黑样本机审拦截数 + 黑样本机审漏过数 = 有机审结果的黑样本数
白样本机审放过数 + 白样本机审误伤数 = 有机审结果的白样本数
任意分子 <= 对应分母
首投数 + 复投数 = 总投放数
```

同时统一：

- 使用 `COUNT(*)`、`COUNT(id)` 还是 `COUNT(DISTINCT id)`。
- 日指标按素材创建日、攻击发生日还是审核完成日。
- `init` 是放过、待审核，还是不进入统计。
- NULL 是否单独归为“无审核结果”。
- 近 7 日窗口是 `[T-6,T]` 还是 `[T-7,T]`。
- 多次审核统计全部过程还是最终结果。

### 3.5 调度、告警和补数闭环

推荐调度顺序：

```text
ODS 到达检查
→ ODS 基础 DQC
→ DIM 更新
→ DWD 清洗
→ DWD 对账
→ DWM 加工
→ JOIN 放大和外键检查
→ ADS 聚合
→ 指标对账
→ Kafka 或大盘发布
```

质量体系还应包含：

- 上游任务依赖和分区到达检查。
- 核心任务基线、业务 SLA 和超时告警。
- 坏数据隔离表，避免问题数据直接进入下游。
- 补数范围、补数审批和补数后对账。
- DQC 负责人、规则变更记录和告警处理手册。
- 修复后按 `${bizdate}` 重跑并再次执行全部质量规则。

## 4. 结合 AI 蓝军项目

### 4.1 生成前供数链路

```text
社区动态、审核、质检、标签、类目 ODS
→ 内容/审核/质检 DWD 和标签/类目 DIM
→ dwm_com_audit_ai_blue_input_detail_di
→ ads_operation_com_ai_blue_2kafka
→ JSON / 外部 Kafka / Dify
```

重点检查：

- `trend_id` 是否唯一。
- 社区内容与审核结果通过 `trend_id=biz_id` 关联后的放大倍数。
- 人审标签 INNER JOIN 过滤了多少内容。
- 机审、人审标签拆分后未匹配标签维表的比例。
- 最终 JSON 中 `trendId`、`url` 和 `data` 是否符合下游契约。

### 4.2 生成后评估链路

```text
蓝军素材、内容、人设、攻击任务、workflow_runs、审核结果 ODS
→ 对应 DWD
→ dwm_com_audit_ai_blue_output_detail_df
→ ads_operation_com_ovewview_target
→ 蓝军大盘和攻防报告
```

重点检查：

- `resource_id` 对应内容数和攻击任务数。
- `trend_id` 对应审核记录数。
- 内容找不到人设、工作流或审核结果的比例。
- DWM 目标粒度是否与 ADS 的 COUNT/SUM 一致。
- 黑白样本、机审、人审、复投、相似度和难度指标能否与明细反查一致。

## 5. SQL 或代码示例

### 5.1 检查分区和行数

```sql
SELECT
    pt,
    COUNT(*) AS row_cnt
FROM yshopping.ods_community_ai_blue_resource_df
WHERE pt='${bizdate}'
GROUP BY pt;
```

### 5.2 检查主键重复

```sql
SELECT
    id,
    COUNT(*) AS cnt
FROM yshopping.ods_community_ai_blue_resource_df
WHERE pt='${bizdate}'
GROUP BY id
HAVING COUNT(*) > 1;
```

### 5.3 逻辑删除对账

```sql
SELECT
    COUNT(*) AS ods_cnt,
    SUM(IF(is_del=0, 1, 0)) AS valid_cnt,
    SUM(IF(is_del=1, 1, 0)) AS deleted_cnt
FROM yshopping.ods_community_ai_blue_resource_df
WHERE pt='${bizdate}';
```

然后验证 DWD 分区行数是否等于 `valid_cnt`。

### 5.4 检查枚举映射覆盖率

```sql
SELECT
    COUNT(*) AS total_cnt,
    SUM(IF(t1.code IS NULL, 1, 0)) AS unmatched_cnt
FROM yshopping.ods_community_ai_blue_content_df t0
LEFT JOIN yshopping.dim_code_desc t1
    ON CAST(t0.sample_attributes AS STRING)=t1.code
   AND t1.table_name='ods_community_ai_blue_content_df'
   AND t1.fields_name='sample_attributes'
WHERE t0.pt='${bizdate}';
```

### 5.5 按业务键取最新审核记录

```sql
SELECT *
FROM (
    SELECT
        t.*,
        ROW_NUMBER() OVER (
            PARTITION BY biz_id, event_code
            ORDER BY tag_time DESC, modify_time DESC
        ) AS rn
    FROM yshopping.dwd_com_audit_detail_df t
    WHERE pt='${bizdate}'
) s
WHERE rn=1;
```

### 5.6 检查 JOIN 放大

```sql
SELECT
    resource_id,
    COUNT(*) AS content_cnt
FROM yshopping.dwd_com_audit_ai_blue_content_df
WHERE pt='${bizdate}'
GROUP BY resource_id
HAVING COUNT(*) > 1;
```

应分别对内容、攻击任务和审核记录执行基数检查，然后比较 DWM 加工前后的总行数和唯一键数量。

### 5.7 按分区覆盖重跑

```sql
INSERT OVERWRITE TABLE yshopping.dwd_com_audit_ai_blue_resource_df
PARTITION(pt='${bizdate}')
SELECT ...
FROM yshopping.ods_community_ai_blue_resource_df
WHERE pt='${bizdate}'
  AND is_del=0;
```

## 6. 官方文档依据

1. [Apache Hive LanguageManual DML](https://hive.apache.org/docs/latest/language/languagemanual-dml/)
   - `INSERT OVERWRITE` 会替换目标表或目标分区的数据，因此可用于按业务日期覆盖重跑。
   - 动态分区字段需要位于 SELECT 结果末尾，并与 `PARTITION()` 中的动态分区顺序一致。
   - 这也是审核 DWD 使用 `pt` 静态分区、`event_code` 动态分区时必须重点核对列顺序的原因。

2. [Apache Spark SQL Built-in Functions](https://spark.apache.org/docs/latest/api/sql/index.html)
   - `row_number()` 按窗口分区和排序为记录分配连续序号，可用于每个业务键取最新状态。

3. [Apache Spark SQL Performance Tuning](https://spark.apache.org/docs/latest/sql-performance-tuning)
   - AQE 可以基于运行时统计调整 JOIN 策略、合并 Shuffle 分区并优化倾斜分区。
   - AQE 解决的是执行计划和性能问题，不能修复错误关联键、错误业务粒度或重复统计口径。

## 7. 项目现状与生产方案

### 7.1 当前项目已经体现的控制

- 多数 DWD、DWM 使用 `INSERT OVERWRITE ... PARTITION(pt='${bizdate}')`，支持同一天覆盖重跑。
- 社区动态、素材和攻击关系在 DWD 过滤 `is_del=0`。
- 使用 `dim_code_desc` 统一内容类型、审核结果、样本属性和人设状态等枚举。
- DWM 和 ADS 已体现分区过滤、业务关联和指标计算逻辑。
- 项目复盘文档已经记录表级血缘、关联键和部分质量风险。

### 7.2 当前 SQL 中需要优先处理的风险

1. 质检 ODS DDL 在最后一个字段后保留了尾随逗号，而且质检 DWD SELECT 读取了源 DDL 中没有定义的 `modify_time`。
2. 审核 DWD 将 `event_code` 同时声明为普通字段和分区字段，需要按实际 Hive/Spark 引擎修正表结构。
3. DWM 输出 DDL 包含攻击用户 `user_id`，但 SELECT 在对应位置直接输出 `t3.attack_task_id`，可能导致后续字段按位置错位。
4. ADS 相似度指标引用了输出宽表不存在的 `person_audit_result`，当前输出字段是 `tag_result_code`。
5. DWM 输入使用 `level3_category_code=t3.biz_id` 关联质检，类目编码与质检业务 ID 的语义需要确认。
6. 审核 DWD 将 `tag_code`、`machine_tag_code` 定义为 BIGINT，DWM 却按逗号字符串执行 `SPLIT`。
7. 内容、攻击任务和审核结果存在多个一对多 JOIN，当前没有在 JOIN 前统一去重，可能放大 ADS 的 COUNT 和 SUM。
8. 两张 ADS 都只有独立 SELECT，没有实际落表 INSERT；当前资料只能证明 JSON 和指标查询逻辑，不能证明完整发布任务。

### 7.3 生产环境建议补充

- 将分区、主键、枚举、外键、行数波动和指标恒等式配置为自动 DQC。
- 在每个关键 JOIN 后持久化行数、唯一键数、空值率和放大倍数。
- 为所有核心指标建立业务口径、技术口径、负责人、统计周期和变更记录。
- 对失败任务实施下游阻断、告警、坏数据隔离、按分区补数和补数后对账。
- 建立产出基线、业务 SLA、值班手册和质量问题复盘机制。

## 8. 面试回答

> 我会从四层保证这条链路的数据质量。首先在建模前明确每张表的业务粒度和唯一键，比如社区内容以 trend_id 为核心，输出宽表明确到 resource_id、trend_id 和 attack_task_id。其次在 ODS 到 DWD 做分区完整性、主键重复、空值、枚举覆盖、逻辑删除和时间转换检查，并通过按业务日期 INSERT OVERWRITE 保证任务可重复执行。DWD 到 DWM 重点检查 JOIN 前后的行数、关联基数和外键缺失率，对于一对多数据使用 ROW_NUMBER 取最新记录，或者明确保留任务级、审核级明细，避免 JOIN 乘积放大。DWM 到 ADS 则用黑样本拦截、黑样本漏过、白样本放过、白样本误伤四类最小数据进行指标对账，保证分子不大于分母，并统一时间、NULL、待审核和复投口径。最后把核心规则做成强 DQC，失败就阻断下游并告警，修复后按分区覆盖重跑。

## 9. 高频追问

### 9.1 为什么 INSERT OVERWRITE 能支持幂等重跑？

因为它会覆盖指定业务分区，而不是在旧分区上继续追加。同一个 `${bizdate}` 重跑后，目标分区应只保留本次计算结果。前提是写入范围准确，不能误覆盖其他分区。

### 9.2 如何判断 JOIN 是否发生异常放大？

比较 JOIN 前后的总行数、唯一业务键数量和每个关联键的最大匹配数。放大不一定都是错误，但必须与目标粒度一致。例如任务级宽表允许一个素材多行，素材级宽表则不能直接保留多条任务记录。

### 9.3 LEFT JOIN 出现 NULL 就是数据质量问题吗？

不一定。刚生成但尚未投放的素材可能没有攻击和审核记录。应根据业务状态定义允许的 NULL，而不是对所有 NULL 一刀切。

### 9.4 为什么不能只使用 COUNT(DISTINCT) 解决重复？

`COUNT(DISTINCT)` 只能缓解某些计数指标的重复，不能修复金额、难度 SUM、状态字段随机匹配和事实行语义错误。根本方案仍是明确粒度并控制 JOIN 基数。

### 9.5 AQE 能解决数据倾斜，也能解决数据重复吗？

不能。AQE 可以优化倾斜 JOIN 的执行方式，但错误关联条件和一对多业务关系产生的重复仍然会保留。

### 9.6 强规则和弱规则如何区分？

会使下游数据不可用或口径错误的规则设为强规则，例如空分区、主键重复、字段错位；允许短期波动但需要观察的规则设为弱规则，例如非核心字段空值率小幅上升。

## 10. 易错点

- 把“任务成功”当成“数据正确”。
- 没有定义粒度就直接查重复。
- 只比较 ODS 和 DWD 总行数，不考虑逻辑删除和业务过滤。
- 认为所有 LEFT JOIN 的 NULL 都是异常。
- 使用 `COUNT(DISTINCT)` 掩盖错误 JOIN。
- 将 `init`、NULL 和真正审核通过混为同一结果。
- 日指标按素材创建日聚合，却解释成攻击发生日。
- 只监控任务失败，不监控行数、枚举和指标异常。
- 把 AQE 等性能优化机制当成业务数据质量保障。
- 将建议建设的 DQC、SLA 和告警平台描述成项目已经完整实现。
