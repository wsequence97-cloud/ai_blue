# 如何维护数仓指标并结合 AI 蓝军项目

## 1. 原问题

在数仓建设实践路线中，关于指标的维护可以怎么做，如何结合 AI 蓝军项目？

## 2. 核心结论

指标维护不能只维护一段 ADS SQL，而要维护“指标定义、数据来源、计算逻辑、数据质量、版本变更和下游影响”这套完整资产。

```text
PRD 指标需求
  -> 指标台账与口径评审
  -> DWD 字段和枚举标准化
  -> DWM 明细粒度确认
  -> ADS 指标 SQL
  -> 数据质量校验
  -> 看板验证与发布
  -> 版本记录和影响评估
```

## 3. 指标台账

每个指标至少记录：指标名称、业务含义、指标类型、统计粒度、时间字段、统计对象、去重键、过滤条件、结果条件、来源表、下游应用、负责人、版本和生效日期。

以本项目的“黑样本机审漏过数”为例：

```text
来源：dwm_com_audit_ai_blue_output_detail_df
统计对象：attack_task_id
条件：ai_blue_sample_code=0
      AND machine_tag_result_code IN ('init', 'pass')
```

正式发布前仍需确认“通过、拒绝、漏过、拦截”的业务方向，不能只根据字段名猜测。

## 4. 分层维护职责

| 层级 | 维护职责 | AI 蓝军项目示例 |
| --- | --- | --- |
| ODS | 保留源系统字段和原始编码 | `tag_result`、`machine_tag_result` |
| DIM | 维护编码和名称映射 | `dim_code_desc` |
| DWD | 统一类型、字段名、时间和枚举 | `tag_result_code`、`tag_result_name` |
| DWM | 固定业务明细粒度，沉淀复用字段 | 素材、内容、攻击和审核宽表 |
| ADS | 面向看板或接口计算结果 | 黑白样本、机审、人审和复投指标 |

新增审核状态时，应优先补充 DIM 和 DWD 标准化逻辑，而不是在每个 ADS SQL 中重复硬编码中文。

## 5. 本项目的关键口径

### 5.1 区分机审标签和机审结果

- `machine_tag_code`：机审识别出的风险标签，一条动态可能有多个标签。
- `machine_tag_result_code`：机审最终处置结果。
- `tag_result_code`：人审处置结果。

机审识别标签不能当成机审最终判断结果。

### 5.2 明确黑白样本方向

```text
黑样本被机审通过：风险漏过
黑样本被机审拦截：机审拦截成功
白样本被机审拒绝：正常内容误伤
白样本被机审通过：正常内容放过
```

### 5.3 明确粒度和去重

```text
素材粒度：resource_id
内容粒度：resource_id + trend_id
任务粒度：resource_id + attack_task_id
```

一个素材可能对应多条内容、多个攻击任务和多条审核记录。指标不能简单使用 `COUNT(*)`，应按业务对象去重：

```sql
COUNT(DISTINCT resource_id)
COUNT(DISTINCT attack_task_id)
```

## 6. 指标质量校验

```sql
-- 检查任务粒度是否重复
SELECT resource_id, attack_task_id, COUNT(*) AS row_cnt
FROM yshopping.dwm_com_audit_ai_blue_output_detail_df
WHERE pt='${bizdate}'
GROUP BY resource_id, attack_task_id
HAVING COUNT(*) > 1;

-- 检查关键关联键为空
SELECT COUNT(*) AS null_resource_cnt
FROM yshopping.dwm_com_audit_ai_blue_output_detail_df
WHERE pt='${bizdate}' AND resource_id IS NULL;

-- 检查审核编码是否完成翻译
SELECT COUNT(*) AS unmapped_cnt
FROM yshopping.dwd_com_audit_detail_df
WHERE pt='${bizdate}'
  AND tag_result_code IS NOT NULL
  AND tag_result_name IS NULL;
```

每天还应做 ODS、DWD、DWM、ADS 行数对账，并检查分子不大于分母、枚举未匹配率、JOIN 放大、关键外键空值和时间口径。黑样本拦截、黑样本漏过、白样本放过、白样本误伤应使用最小样例反查明细。

## 7. 指标变更管理

每次变更记录：

```text
指标名称、旧口径、新口径、变更原因、生效日期、影响表、影响报表、是否回刷历史、验证结果
```

例如“攻击次数”从宽表行数改成攻击任务去重数时，需要同步评估 DWM 粒度、ADS 是否改为 `COUNT(DISTINCT attack_task_id)`、看板历史数据是否回刷，以及项目文档是否同步。

## 8. 面试回答

> 我会先建立指标台账，统一维护指标定义、分子分母、统计粒度、时间字段、去重键、来源表和下游应用。在 AI 蓝军项目中，ODS 保留原始审核编码，DIM 维护编码翻译，DWD 统一字段和枚举，DWM 明确素材、内容、攻击任务的业务粒度，ADS 再计算黑白样本、机审、人审、复投、相似度和难度指标。同时通过主键重复、空值、枚举匹配、行数对账、JOIN 放大和分子分母校验保障指标质量。指标变更时记录新旧口径、生效时间和影响范围，必要时按分区回刷历史数据。

## 9. 项目现状与生产方案

当前资料已整理出 PRD 17 类业务指标、2 张 ADS 表，以及大盘 ADS 的 25 个物理字段；但不能据此证明所有 PRD 指标都已在现有 ADS SQL 中完整落地，也不能证明指标审批、自动告警和历史回刷流程已经上线。

生产环境建议将指标台账、DQC 规则、SQL 版本、字段血缘和发布记录纳入统一指标管理流程。

## 10. 易错点

- 把 PRD 17 类指标理解成 ADS 的 17 个字段。
- 把 ADS 25 个物理字段理解成 25 类业务指标。
- 用 `COUNT(*)` 代替业务对象去重。
- 把 `machine_tag_code` 当成机审结果。
- 只修改 ADS，不同步 DWD、DIM 和指标文档。
- 未确认时间字段就直接比较日指标。
- 忽略一对多 JOIN 导致指标被放大。

## 11. 复盘检查清单

- [ ] 能说明指标的业务含义、分子、分母和去重键。
- [ ] 能说清 ODS、DIM、DWD、DWM、ADS 各层职责。
- [ ] 能区分机审标签、机审结果和人审结果。
- [ ] 能说明 `resource_id`、`trend_id`、`attack_task_id` 的粒度差异。
- [ ] 能写出指标重复或枚举未匹配校验 SQL。
- [ ] 能说明指标变更如何评估下游影响和历史回刷。
