## 7. 针对 MapReduce 而言，Spark 有什么优势？
相比 MapReduce，Spark 的优势主要体现在执行模型、中间结果复用和资源复用三个方面。
第一，Spark 会根据转换算子构建 DAG，并按照 Shuffle 边界划分 Stage。窄依赖算子可以在同一个 Stage 内通过流水线连续执行，只有宽依赖通常才需要 Shuffle。MapReduce 的执行模型相对固定，复杂计算往往要拆成多个 Job，Job 之间通常需要把中间结果写入 HDFS，再由下一个 Job读取，因此磁盘和调度开销更大。
第二，Spark 可以通过 cache 或 persist 将重复使用的数据保存在内存或磁盘中，比较适合迭代计算、交互式分析和同一份中间数据被多次复用的场景。MapReduce 对中间结果的复用通常依赖文件系统。
第三，Spark 的 Executor 在 Application 运行期间可以持续复用，执行完一个 Task 后还能继续执行后续 Task；MapReduce 不同任务之间的启动和资源调度开销相对更明显。
此外，Spark 同时提供 SQL、流处理、机器学习等计算能力，开发接口也比原生 MapReduce 更丰富。但 Spark 并不是所有场景都一定更快，如果 Shuffle 很重、数据倾斜严重或内存配置不合理，仍然可能出现性能问题。
## 8. MapReduce 原理流程
MapReduce 的整体执行流程可以分为 Map、Shuffle 和 Reduce 三个核心阶段：

   Map 阶段：输入数据被切分成多个分片，由多个 MapTask 并行处理，每个 MapTask 输出中间的 Key-Value 数据。
   Shuffle 阶段：Map 输出会先按照 Key 进行分区，相同 Key 会被分配到同一个 Reduce 分区；同时 Map 端会进行排序和落盘，Reduce 端再拉取属于自己的数据并做归并、分组。Shuffle 的目的就是让相同 Key 的数据汇聚到一起。
   Reduce 阶段：Reducer 对每个 key 对应的一组 values 做聚合、统计或者关联，最后把结果写入 HDFS。

所以 MapReduce 的核心思想就是：Map 做分布式并行计算，Shuffle 按 Key 重新组织数据，Reduce 对相同 Key 做汇总计算。

如果追问“Shuffle 具体怎么做”，再展开：
Map 输出先进入内存缓冲区，按照 Partitioner 分区并排序，达到阈值后 Spill 到本地磁盘，多个 Spill 文件进行归并；Reduce 再从各个 Map 节点拉取属于自己分区的数据，继续归并排序并按 Key 分组。

## 12. Hive 产出的小文件太多，小文件本身会带来什么样的一些危害？HDFS 有很多小文件，会带来什么样的问题？
Hive 产生大量小文件，首先会给 HDFS 的 NameNode 带来压力。因为 NameNode 需要在内存中维护每个文件、目录、Block 及副本位置等元数据。即使每个文件的数据量很小，也要单独维护一份文件和 Block 元数据。小文件数量过多会占用更多 NameNode 内存，并增加文件创建、查询、删除和获取 Block 位置等 RPC 请求，最终限制集群能够管理的文件总量。
第二，会降低 Hive 查询效率。查询大量小文件时，需要频繁访问 NameNode 获取文件位置，并进行大量文件打开、关闭和连接操作。小文件还可能生成大量 InputSplit 和 MapTask，真正计算的数据很少，但任务启动、资源申请和调度时间很多。
## 13. 从代码角度，会用哪些方式去实现一个去重的目标？
从代码角度做去重，我会先确认重复键和保留规则。如果是整行完全重复，可以使用 DISTINCT；如果只需要得到唯一业务键，可以使用 GROUP BY。如果业务主键相同但其他字段不同，并且需要保留最新或优先级最高的一条，我一般使用 ROW_NUMBER()，按照业务主键分组、更新时间倒序，再取 rn=1。多个数据集合并时可以使用 UNION DISTINCT
## 14. DISTINCT 去重效率比较低的原因
DISTINCT 效率相对较低，主要是因为它要保证全局去重。相同字段组合可能分布在不同节点，所以通常需要按照去重字段进行 Shuffle，把相同数据汇集到同一个下游 Task，再通过 Hash 聚合或排序完成去重。字段越多、数据越宽，网络传输、序列化和比较成本越高；如果内存不足还会发生磁盘溢写。如果去重字段中存在大量空值或默认值，还可能造成数据倾斜。

## 18. 数仓建模相关，DWD 层建设方法是怎么样的？可以结合自己的一些经验
我建设 DWD 时，首先会根据业务边界划分数据域，再识别域内的原子业务过程。围绕每个业务过程，先定义一行数据代表什么、业务主键是什么，以及采用事务明细还是状态快照，避免不同粒度的数据混在一张表中。  
第二步是梳理 ODS 来源和字段映射，完成类型、命名、时间和枚举口径统一。对于逻辑删除、测试数据和明确无效的数据，会按照业务规则处理；对于不能确定的异常数据，不会直接删除，而是保留原值或增加异常标识。JSON 字段只解析稳定且高频使用的内容，同时保留必要的原始信息用于追溯。  
第三步是根据上游变化方式设计全量、增量或快照策略，并处理去重、迟到数据、任务重跑和幂等问题。最后通过数据量、主键唯一性、空值、枚举和上下游对账来保证质量。  
在蓝军项目中，我按照内容、审核、素材、人设、攻击关系和工作流运行等不同业务过程建设或复用 DWD 明细。例如审核明细统一机审、人审和处置枚举，素材明细过滤逻辑删除数据，工作流明细解析输入 JSON 中的业务 ID。这样既保留原子明细，也为后续 DWM 场景宽表提供口径统一的数据。
## 19. 如何评价数仓模型做得好还是不好？会从哪些方面评价？
我评价一个数仓模型，不会只看分了多少层，而是从业务、数据和技术三个方向判断。
第一是业务正确性，要看业务域、原子业务过程、表粒度和指标口径是否清楚，是否会因为一对多 Join 造成重复统计。
第二是数据可用性，包括主键唯一性、完整性、上下游对账、产出时效以及重跑和迟到数据处理。
第三是模型复用性和分层合理性，公共事实与维度是否统一沉淀，下游是否存在重复加工或跨层依赖。
第四是性能和成本，要关注分区裁剪、小文件、Join 放大、数据倾斜、任务 SLA 和资源消耗。
最后还要看可维护性和扩展性，例如命名、文档、血缘是否清楚，新增业务时能否低成本扩展。
所以好的数仓模型应该同时做到业务口径准确、数据质量稳定、公共逻辑可复用、计算成本可控，并且能够持续演进。
## 20. 建设好了数仓任务之后，会做哪些方面的质量监控？
	上线前：
		1.试跑，第一个看运行时间有可能数据倾斜或者数据膨胀导致它跑不完，或者有没有报错，就是校验代码的准确性
		2.数据探查，先把“真实数据长什么样”摸清楚，避免SQL逻辑建立在错误假设上。写sql看数据分布最大最小值，最大字段长度、空值，去重前后的行数
		3.数据比对，比如新增字段，在线下加了1个字段变成101个字段，用前一百个字段进行比较，看对线上是否造成影响。
		4.抽样探查，其实就是随机挑几条真实业务数据，用业务主键从DWD一路追到DWM、ADS。比如抽一条黑样本，我会确认它实际投放的内容、最终审核状态和DWM记录是否一致，再看ADS有没有把它正确统计成拦截或者漏放。简单说就是挑几条数据人工走完整条链路，看有没有丢、重复或者算反。
		5.依赖探查，例如前置DWM新增质检结果字段后，如果引用了新的质检DWD，就必须增加“质检DWD成功后再运行前置DWM”的依赖，否则任务虽然可能执行成功，但新增字段会全部为空。
		6.让mentoe或者同事去对你的代码code review

	上线中：
		1. 配置DQC和SLA监控告警，DQC主要配置了包括表不为空表行数波动主键唯一主键不为空，空值比例等，防止每日问题数据向下游流出，保障每日任务正常运行
		2.上线后回补数据，数据回补主要是解决代码变更后历史数据和新逻辑不一致的问题。比如新增字段、修改Join逻辑或者修复指标口径后，新任务只会影响之后的数据，历史分区还是旧结果，所以需要按影响范围重新执行历史分区的DWD、DWM、ADS加工。如果是全量数据则跑t-1即可，如果是增量数据需要进行补数据，为了检测生产环境是否有访问表的权限，如果没有的话生产环境运行代码也会报错，同时也是为了刷新数据后续交付。

	上线后：
		1.上线后完成和下游的问题群建设，及时登记问题，更新问题进展，以及后续运维
		2.上线发布后需要让数据产品/mentor/自己再次看一下报表情况，再去看一下指标是否有异常
		3.将xxx业务指标维护至指标管理中心统一管理，并提供详细的指标说明
## 21. 缓慢变化维有了解过吗？
缓慢变化维解决的是维度属性发生变化后，历史如何保留的问题。常见有三种处理方式。
Type 1 是直接覆盖旧值，适合数据纠错或只关心当前状态，但会丢失历史；
Type 2 是属性变化时关闭旧版本并新增一条记录，通过生效时间、失效时间和当前标识维护历史，也就是常说的拉链表，适合需要还原事实发生时维度状态的场景；
Type 3 是增加当前值和历史值字段，只适合保留有限次变化。实际选择时我会先和业务确认历史报表是按当前口径分析，还是按事件发生时的口径分析。
对于 Type 2，我会比较当天数据和历史当前版本，新数据直接插入，未变化数据保留，发生变化的数据关闭旧版本并插入新版本，同时处理删除、迟到数据和任务重跑问题。

## 25. 工作涉及跨部门协作或者跟其他同事交流时，怎么样去缓解、提升各方面的效率？
跨部门协作时，我主要从三个阶段提高效率。沟通前，我会先完成基础排查，把问题、影响范围、相关表字段和需要对方确认的内容整理清楚，避免直接抛出模糊问题。沟通中，我会先对齐业务目标、交付物、职责边界、截止时间和验收标准，再把需求转换成明确的数据粒度、字段口径、更新频率和数据契约。对于复杂需求，我会先提供样例数据或小范围试跑结果，让业务方提前确认。沟通后，我会把结论、待办、负责人和时间点沉淀到文档或任务中，并持续跟进。如果出现口径冲突或进度风险，我会带着排查结果和备选方案及时升级。我的理解是，沟通效率不只是回复得快，而是减少信息差、避免重复确认和返工，最终让问题形成闭环。
