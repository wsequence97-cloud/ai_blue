## 10. 大模型经过处理之后的结果，也就是拦截率那些，这部分是服务于谁的？
攻防结果指标主要服务蓝军运营和审核策略团队。运营通过不同风险标签、内容类型和样本难度下的拦截率、漏过率和误伤率，识别审核系统的薄弱点，并指导下一轮样本生产和攻击任务；审核策略团队则根据漏过和误伤情况优化规则、模型阈值及审核策略。产品经理更多关注整体趋势、人效和项目目标是否达成，用于安排产品迭代。算法团队也可以根据不同生成方式和样本类型的攻击效果，优化Prompt和生成策略。因此这套数据是多角色共用，但运营和审核策略是最直接的业务使用方。

## 12. 讲讲数仓分层，为什么要这么做，每一层在做什么？
分层的目的是以空间换时间:
1.使数据更清晰，简化复杂问题。将复杂需求简单化拆解成多个步骤解决，每层去完成各自对数据的处理。
2.减少重复开发，提升开发效率。通过大量的预处理，建设数仓中间层，提高数据复用性。
3.数据血缘追踪，便于定位问题。分层能够清晰表和任务的上下游，知道下游哪个模块在使用，便于排查问题和后期维护。

（为什么建dwd跟dwm需要清楚粒度和业务主键：因为我要先知道一行到底代表什么，再知道用什么字段能唯一认出这一行。尤其DWM会Join很多表，如果这两个没定清楚，很容易一对多把一条数据变成多条，最后导致重复数据和指标算错。）

ods:
主要作用是贴源留存、隔离业务库、便于追溯和重算。
将不同来源的数据库数据同步过来，eg:素材、生成内容、用户人设等，保持数据原始性。

dwd:主要讲后置链路
核心是把“源系统怎么存”转换成“数仓怎么规范描述业务事实”。
首先会根据业务边界划分数据域，再识别域内的原子业务过程。围绕每个业务过程，先定义一行数据代表什么、业务主键是什么，以及采用事务明细还是状态快照，避免不同粒度的数据混在一张表中。  
第二步是梳理 ODS 来源和字段映射，完成类型、命名、时间和枚举口径统一。对于逻辑删除、测试数据和明确无效的数据，会按照业务规则处理；对于不能确定的异常数据，不会直接删除，而是保留原值或增加异常标识。JSON 字段只解析稳定且高频使用的内容，同时保留必要的原始信息用于追溯。  
第三步是根据上游变化方式设计全量、增量或快照策略，并处理去重、迟到数据、任务重跑和幂等问题。最后通过数据量、主键唯一性、空值、枚举和上下游对账来保证质量。  
在蓝军项目中，我按照内容、审核、素材、人设、攻击关系和工作流运行等不同业务过程建设或复用 DWD 明细。例如审核明细统一机审、人审和处置枚举，素材明细过滤逻辑删除数据，工作流明细解析输入 JSON 中的业务 ID。这样既保留原子明细，也为后续 DWM 场景宽表提供口径统一的数据。

dwm:
先明确分析主题和一行代表什么，再选择核心DWD作为主表，将同流程的表进行关联，产出一张明细大宽表，主要解决的事情1.业务方需要取明细数据但是不具备写sql能力，每次写的话需要询问其他人，而且他的需求不能通过一张表去解决的。2.DWM层统一关联维表，将高频维度属性沉淀到主题宽表中。这样当维度口径发生调整时，可以统一修改并回刷DWM，避免多张DWD分别维护和回刷，保证下游使用的维度口径一致。

dws:1.指标口径的统一；2.指标的复用性

ads:
对DWM数据进行最终汇总、指标计算和格式适配，让业务方可以直接使用。
后置ADS主要面向蓝军运营、审核策略和产品分析场景，基于后置DWM中“一次实际攻击投放及其审核结果”的明细数据，按照统计日期、样本类型、难度、内容类型、风险标签等维度进行汇总，计算攻击次数、已审核样本数、黑样本拦截数和漏过数、白样本放行数和误伤数，以及对应的拦截率、漏过率和误伤率，最终交付给报表和指标平台使用。

## 14. DWD 或者 DWM 中应该做什么样的维度和指标？项目中 DWD 和 DWM 各表是怎样划分的？比如 DWM 为什么划分两张表，为什么放这些维度和指标？
DWD层是按照原子业务事实来划分的，而不是把所有数据直接拼成宽表。例如内容、审核、质检、蓝军素材、生成内容、用户人设、攻击任务关系和Dify工作流运行，分别有各自的DWD明细表，因为它们的一行数据代表不同业务事实，主键和生命周期也不同。
DWM层则按照稳定业务场景来组织。生成前输入DWM以社区帖子为主，一行表示当日发布的一条内容及其类目、审核标签和质检上下文，主要给Dify提供结构化参考数据；生成后输出DWM以蓝军素材为主线，关联生成内容、人设、攻击任务、工作流和审核结果，主要服务于投放效果和风控复盘。  
两张DWM不能简单合并，因为它们的主事实、粒度和下游不同：前者是帖子粒度、服务模型输入，后者是素材或任务粒度、服务效果评估。强行合并会混合生成前后的生命周期，也容易因为内容、任务和审核的一对多关系导致Join放大。  
因此，我理解DWD解决的是“每种事实如何规范保存”，DWM解决的是“为一个具体场景怎样组合这些事实”；建DWM时最关键的是先明确目标粒度和Join基数。

事务事实表：一行表示一次明确发生的业务事件，通常只追加，不回写历史。eg:4行

## 17. Spark 执行原理以及提交流程

提交阶段，客户端先从 RM 获取 applicationId，把 Jar、依赖和配置上传到 HDFS，再向 RM 提交应用。RM 分配 Container 并由 NodeManager 启动 AM；Cluster 模式下 Driver 随 AM 启动。Driver 初始化 SparkContext 后，通过 AM 向 RM 申请 Executor 资源，各节点 NM 启动 Executor，Executor 再向 Driver 注册。

运行阶段，转换算子只构建血缘，Action 才触发 Job。Driver 根据 Shuffle 边界把 Job 切成多个 Stage，每个 Stage 再按分区拆成 Task，分发给 Executor 执行。Executor 执行完一个 Task 后可以继续复用，直到整个 Application 完成再释放资源。
## 18. Spark Shuffle 是做什么事情？
Spark Shuffle 本质上是数据在不同分区、不同 Executor 之间重新分发的过程。它通常发生在宽依赖算子，例如 groupByKey、reduceByKey、Join 或 repartition。
第一阶段是 Shuffle Write：上游 Task 根据分区器，例如按 key 的 Hash，将自己的结果拆成多份，分别对应下游不同分区，并写成可供下游读取的 Shuffle 数据。
第二阶段是 Shuffle Read：下游每个 Task 从所有上游 Task 拉取属于自己分区的数据；这样相同 key 的数据就能汇集到同一个 Task 中，再进行聚合、Join 或排序等后续处理。
所以 Shuffle 的代价主要来自跨节点网络传输、磁盘读写和数据排序/合并；没有跨分区依赖的窄依赖通常不需要 Shuffle。
