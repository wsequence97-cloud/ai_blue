## 5. 整个过程中如何保证数据的稳定性
	上线前：
		1.试跑，第一个看运行时间有可能数据倾斜或者数据膨胀导致它跑不完，或者有没有报错，就是校验代码的准确性
		2.数据探查，先把“真实数据长什么样”摸清楚，避免SQL逻辑建立在错误假设上。写sql看数据分布最大最小值，最大字段长度、空值，去重前后的行数
		3.数据比对，比如新增字段，在线下加了1个字段变成101个字段，用前一百个字段进行比较，看对线上是否造成影响。
		4.抽样探查，其实就是随机挑几条真实业务数据，用业务主键从DWD一路追到DWM、ADS。比如抽一条黑样本，我会确认它实际投放的内容、最终审核状态和DWM记录是否一致，再看ADS有没有把它正确统计成拦截或者漏放。简单说就是挑几条数据人工走完整条链路，看有没有丢、重复或者算反。
		5.依赖探查，例如前置DWM新增质检结果字段后，如果引用了新的质检DWD，就必须增加“质检DWD成功后再运行前置DWM”的依赖，否则任务虽然可能执行成功，但新增字段会全部为空。
		6.让mentoe或者同事去对你的代码code review

	上线中：
		1. 配置DQC和SLA监控告警，DQC主要配置了包括表不为空表行数波动主键唯一主键不为空，空值比例等，防止每日问题数据向下游流出，保障每日任务正常运行
		2.上线后回补数据，数据回补主要是解决代码变更后历史数据和新逻辑不一致的问题。比如新增字段、修改Join逻辑或者修复指标口径后，新任务只会影响之后的数据，历史分区还是旧结果，所以需要按影响范围重新执行历史分区的DWD、DWM、ADS加工。如果是全量数据则跑t-1即可，如果是增量数据需要进行补数据，为了检测生产环境是否有访问表的权限，如果没有的话生产环境运行代码也会报错，同时也是为了刷新数据后续交付。

	上线后：
		1.上线后完成和下游的问题群建设，及时登记问题，更新问题进展，以及后续运维
		2.上线发布后需要让数据产品/mentor/自己再次看一下报表情况，再去看一下指标是否有异常
		3.将xxx业务指标维护至指标管理中心统一管理，并提供详细的指标说明
## 6. 对DWM层的理解，以及和DWS层的区别
DWM 主要解决三个问题。第一，DWD 是按原子业务过程建设的，一个完整分析主题往往需要关联多张 DWD，所以 DWM 会围绕稳定的分析主题和目标粒度，把多个业务过程进行整合，降低下游重复 JOIN 的成本。第二，DWM 会关联统一的 DIM，并把常用维度属性退化到主题宽表中，形成统一的维度消费入口，避免多个下游重复维护维度逻辑。第三，DWM 会提前处理一对多关联、去重、状态收敛和时间语义，为 DWS、ADS 提供统一的明细数据底座。
DWM 和 DWS 最大区别在粒度和用途。DWM 仍然以主题明细为主，保留比较完整的业务上下文；DWS 则是在 DWM 或 DWD 基础上，按照公共分析粒度提前汇总可复用的指标，比如样本量、拦截量、漏放量等，为多个 ADS 提供公共指标能力。

## 9. 知道如何构建Skill吗？一个Skill里面包含哪些内容？
我当时是从实际 SQL Code Review 场景出发做的。首先先定义 Skill 的边界，它主要做静态 SQL 检查，不直接运行任务；然后确定支持 Hive、Spark、Flink、MaxCompute 等 SQL 类型。接下来我把平时 Code Review 的经验拆成语法正确性、数据质量、SQL 性能、代码规范和逻辑问题五类规则，例如 GROUP BY 完整性、ROW_NUMBER 排序、NULL 处理、分区裁剪、大表 JOIN 和数据倾斜风险等。再根据问题影响把结果分成严重问题、潜在风险和优化建议，并规定统一的 CR 报告格式。最后我会构造一些有已知问题的 SQL 作为测试用例，验证 Skill 是否能准确识别这些问题，再持续补充规则。

my-skill/
├── SKILL.md          # 必须，Skill 的核心
├── scripts/          # 可选，可执行脚本
├── references/       # 可选，参考资料/知识
└── assets/           # 可选，模板、示例、静态资源等
按照官方的组织方式，Skill 是一个以 SKILL.md 为核心的目录，SKILL.md 负责描述 Skill 及执行指令，同时可以按需附带 scripts、references、assets 等资源；我这个 SQL Review Skill 的核心就是把 SQL Code Review 的检查流程和专家规则固化在 SKILL.md 中。
